# Crakbit Chain v0.8 Alpha — Resumable Snapshot Transfer + Recovery Hardening

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.8 focuses on making the v0.7 quorum snapshot recovery path safer to operate over larger state and clearer to diagnose after a crash or snapshot bootstrap.

## What v0.8 Adds

### Bounded chunked snapshot transport

A validator can expose its current signed snapshot as a bounded chunk bundle:

```text
GET /snapshot/bundle/manifest
GET /snapshot/bundle/chunk/{artifact_sha256}/{index}
```

The manifest commits to:

- the canonical serialized artifact hash,
- total byte size,
- configured chunk size,
- chunk count,
- every chunk size,
- every chunk SHA-256 hash.

Default chunks are 64 KiB. The implementation enforces explicit per-chunk, total-size and chunk-count limits before reassembly.

This framing does not replace snapshot signatures. The reconstructed validator envelope is still verified by the snapshot layer and must participate in the existing strict `>2/3` quorum certificate.

### Resumable chunk cache

The CLI adds:

```bash
crakchain snapshot-fetch-chunked \
  --genesis runtime/genesis.json \
  --output runtime/snapshot-cert.json \
  --cache-dir runtime/snapshot-cache
```

For each validator, the command:

1. requests a bundle manifest,
2. creates a cache directory keyed by validator and artifact hash,
3. validates already-downloaded chunks,
4. skips chunks whose size and SHA-256 are still valid,
5. downloads missing/corrupt chunks,
6. verifies the complete artifact hash,
7. parses the reconstructed signed snapshot envelope,
8. builds a quorum certificate only if enough validators signed identical state.

Re-running the command can therefore reuse verified chunks for the same immutable cached bundle.

### Snapshot import journal

SQLite already makes the snapshot database mutation transactional. v0.8 adds a sidecar intent journal so an operator can distinguish a clean state from a process that was interrupted around the import operation.

The journal is stored next to the chain database as:

```text
snapshot-import.journal.json
```

The importer records the target certificate hash, state root, height and block hash before mutating the database. After a successful commit the journal is marked committed and removed.

If a crash leaves the journal behind:

- re-running the **same** import can safely reconcile a database that already committed the certificate,
- a fresh database can retry the same certificate,
- a different certificate is refused until the operator reviews the unfinished journal.

Operational status is exposed at:

```text
GET /recovery/import-journal
```

### Snapshot-base-aware history APIs

A node bootstrapped from a state snapshot has certified current state but does not magically recover historical block bodies before the snapshot base.

v0.8 makes this explicit:

```text
GET /history/status
GET /history/block/{height}
```

`/history/status` reports the snapshot base height/hash and the first height whose full block body can exist locally after bootstrap.

If a requested historical block is below/equal to the snapshot base and is not stored locally, `/history/block/{height}` returns HTTP `410 Gone` with a structured explanation instead of pretending the block simply never existed.

### Recovery status retained

The v0.7 endpoint remains available:

```text
GET /recovery/status
```

and continues to report snapshot bootstrap metadata and durable peer replay-store mode.

## Security Properties

v0.8 snapshot transfer protects against accidental/corrupt chunk substitution by validating every chunk hash and the complete artifact hash before JSON parsing. The snapshot envelope/certificate signatures remain the source of state authenticity.

The transfer layer enforces bounded artifact and chunk sizes to reduce uncontrolled memory use during development recovery operations.

The import journal improves crash visibility but is not a distributed recovery protocol. SQLite transaction atomicity remains the mechanism that prevents partial account-state commits.

## What v0.8 Does Not Claim

v0.8 does **not** make Crakbit Chain production-ready.

Important blockers remain:

- the conservative consensus lock still lacks a mature proof-based cross-round unlock rule,
- validator transport can require HTTPS but does not yet provide a reviewed mTLS/certificate lifecycle,
- snapshot bootstrap does not reconstruct pre-snapshot blocks or transactions,
- historical archive/remote-history services are not implemented,
- long-running Byzantine/partition/latency/load tests are still required,
- production key management and validator-set economics are not implemented,
- no independent consensus/network audit has been completed.

## Example Recovery Flow

```bash
# 1. Build a quorum certificate using resumable chunks
crakchain snapshot-fetch-chunked \
  --genesis runtime/genesis.json \
  --output runtime/snapshot-cert.json \
  --cache-dir runtime/snapshot-cache

# 2. Verify the certificate
crakchain snapshot-verify \
  --snapshot runtime/snapshot-cert.json \
  --genesis runtime/genesis.json

# 3. Import only into a fresh node database
crakchain snapshot-import \
  --snapshot runtime/snapshot-cert.json \
  --genesis runtime/genesis.json \
  --data runtime/recovered-node

# 4. Or bootstrap a node directly from the certificate
crakchain node \
  --genesis runtime/genesis.json \
  --key runtime/node4/validator.json \
  --data runtime/node4-recovered \
  --bootstrap-snapshot runtime/snapshot-cert.json \
  --port 9204
```

## Next Engineering Phase — v0.9

Planned priorities:

1. Replace/review the conservative consensus lock with a mature proof-based BFT lock/unlock design, or migrate to a reviewed BFT core.
2. Add mutually authenticated encrypted validator transport with certificate pinning and rotation.
3. Add archive/history synchronization design for snapshot-bootstrapped nodes.
4. Add database corruption, abrupt-power-loss and restart recovery harnesses.
5. Add long-running partition, latency, Byzantine-behavior and load testing.
6. Add Prometheus/Grafana dashboards and alert rules.
7. Add public-testnet deployment manifests and validator operator runbooks.
8. Add faucet abuse controls and stronger wallet/explorer testnet UX.
9. Define validator key-management and incident-response procedures.
10. Commission independent consensus/network review before any public-value use.
