# Crakbit Chain v0.20 Alpha — Upgrade Compatibility & Validator Lifecycle Rehearsal

**Status:** public-testnet / review-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.20 focuses on safe upgrade mechanics and validator-lifecycle rehearsal without pretending that a live production validator-set change has been implemented or independently reviewed.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Versioned external-application schema

New module:

```text
crakbit_chain/schema_migrations_v20.py
```

v0.20 introduces explicit external-application schema version `20`. Existing `crakbit-execution/2` databases without an explicit schema-version key are treated as the v0.19 baseline (`19`).

New commands:

```text
crakchain schema-status
crakchain migration-dry-run
crakchain migration-copy
```

The migration path is deliberately **offline-copy-first**:

- the source database is never modified by the migration command,
- SQLite's backup API creates a consistent copy,
- the source logical fingerprint is checked before/after backup,
- v19 → v20 migration runs only on the copy,
- pre-existing logical application state must remain byte-independent but logically identical,
- rollback is rehearsed on another disposable copy,
- rollback must restore the v19 logical fingerprint before the migration is accepted.

The v20 migration adds only upgrade/operations metadata tables and the schema-version marker. It does not rewrite balances, nonces, transactions, external commits or consensus hashes.

Example dry run:

```bash
crakchain migration-dry-run \
  --source runtime/comet-app
```

Create an explicit migrated copy:

```bash
crakchain migration-copy \
  --source runtime/comet-app \
  --output runtime/migrated-v20/chain.sqlite3
```

Do not replace a live node database merely because this command succeeds. Stop/restart, backup, state-sync and rollback procedures still need an operator-reviewed deployment plan.

## 2. Protocol / schema compatibility matrix

New module:

```text
crakbit_chain/compatibility_v20.py
```

Commands:

```text
crakchain compatibility-matrix
crakchain compatibility-check
```

The current v0.20 compatibility declaration is conservative:

- package: `0.20.0a1`,
- execution protocol: `crakbit-execution/2`,
- supported application schemas: `19`, `20`,
- recommended schema: `20`,
- declared CometBFT candidate: `v0.40.0`,
- live validator updates: disabled,
- production mainnet readiness: false.

A v19 database remains readable for migration/rehearsal compatibility, but v20 is the recommended schema for v0.20 testnet exercises.

## 3. Offline upgrade rehearsal

New module:

```text
crakbit_chain/upgrade_rehearsal_v20.py
```

Command:

```text
crakchain upgrade-rehearse
```

The rehearsal:

1. loads the expected genesis,
2. copies and migrates the external application DB,
3. verifies rollback on a disposable copy,
4. runs SQLite `integrity_check`,
5. verifies genesis identity,
6. runs the v0.20 compatibility gate,
7. emits a machine-readable report.

Example:

```bash
crakchain upgrade-rehearse \
  --genesis runtime/genesis.json \
  --source-data runtime/comet-app \
  --output-data runtime/upgrade-rehearsal-v20 \
  --cometbft-version v0.40.0 \
  --report runtime/evidence/upgrade-v20.json
```

The report explicitly records:

```text
source_modified = false
live_node_upgraded = false
production_mainnet_ready = false
```

## 4. Signed migration / rollback evidence

New module:

```text
crakbit_chain/migration_evidence_v20.py
```

Commands:

```text
crakchain migration-evidence-build
crakchain migration-evidence-verify
```

The signed artifact binds:

- exact Git source commit,
- source and target schema versions,
- source/output logical fingerprints,
- rollback-verification result,
- upgrade-rehearsal report SHA-256,
- a dedicated Ed25519 migration-evidence signer.

This is operator evidence, not an independent audit certificate.

## 5. Validator lifecycle drill plans

New module:

```text
crakbit_chain/validator_lifecycle_v20.py
```

Commands:

```text
crakchain validator-plan-build
crakchain validator-plan-verify
```

Supported research drill types:

- `join`,
- `remove`,
- `replace`.

A signed lifecycle plan records:

- exact source commit,
- chain/genesis identity,
- modeled validator set before and after,
- deterministic validator-set hashes,
- the CometBFT-style public-key/power update set,
- the FinalizeBlock emission height and modeled effective height,
- dedicated signer identity.

CometBFT validator updates returned at finalized height `H` affect the validator set at `H+2`, so the plan records both heights explicitly.

### Important safety boundary

v0.20 **does not emit these updates into live CometBFT consensus**. The plan deliberately contains:

```text
live_abci_validator_updates_emitted = false
consensus_change_applied = false
```

Why: validator-set changes must be deterministic application state. Injecting an operator-local update plan directly into one validator would risk different application responses across nodes. A future phase must define a reviewed on-chain or otherwise deterministic replicated authorization path before enabling live ABCI validator updates.

The v0.20 tooling is therefore suitable for join/remove/replace **rehearsal and review**, not live production validator management.

## 6. Tests / CI

v0.20 adds regression coverage for:

- v19 schema detection,
- v19 → v20 copy migration,
- source-state preservation,
- rollback verification,
- compatibility pass/fail cases,
- full upgrade rehearsal,
- signed migration evidence and tamper rejection,
- signed validator-lifecycle plans,
- prevention of removing the final modeled validator.

The existing blockchain workflow continues to run Python and Go bridge tests, reproducible Python/Go builds and SBOM generation.

## External gates still open

Repository code cannot honestly complete the following by itself:

1. long-running four-validator operation across independently managed hosts/providers,
2. live clean-host CometBFT state-sync recovery with app-hash convergence,
3. real partition/packet-loss/latency/process-kill/load campaigns,
4. real remote-signer/HSM-equivalent validator custody and recovery drills,
5. a multi-operator genesis ceremony with independently held keys,
6. independent consensus/application/network/browser-wallet review,
7. complete transitive release SBOM and independent reproducible builds,
8. a reviewed deterministic live validator-set update mechanism,
9. production multi-edge DDoS/WAF/capacity engineering,
10. finalized validator economics/incentives and applicable legal/regulatory review.

## Suggested next phase — v0.21

v0.21 should focus on a **deterministic validator-governance research path and upgrade activation protocol**:

- define a replicated authorization object for validator-set changes,
- commit pending validator changes into deterministic application state,
- include lifecycle state in the application hash,
- emit ABCI validator updates only from replicated committed state,
- add activation-height replay/restart tests,
- add multi-node join/remove/replace lab tests,
- add schema migration activation/rollback coordination across a full testnet,
- preserve the production launch block until external review and operations gates are actually satisfied.

Until those gates are satisfied, use **public testnet**, **review candidate** or **mainnet-candidate infrastructure** — not production mainnet.
