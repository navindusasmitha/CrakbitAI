# Crakbit Chain v0.11 Alpha — Validator mTLS, Certificate Pinning & Fault-Harness Foundation

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.11 focuses on validator transport identity, certificate trust, repeatable transport faults and an explicit consensus architecture decision. It does **not** claim that the current Python consensus is production-safe.

## Consensus architecture decision

`docs/ADR-0001-consensus-direction.md` records the project decision to stop extending the current Python research consensus as if it were a production BFT protocol. Before any real-value mainnet planning, Crakbit will evaluate migration of the execution/state layer to an established independently reviewed BFT core, using a Tendermint/CometBFT-style protocol as the primary architectural reference.

The current proposal/view-change/prevote/precommit implementation remains useful for devnet research only.

## v0.11 transport security

The node now has an optional operator-managed validator transport layer:

```text
Ed25519 request signature + challenge response
                +
TLS server authentication
                +
TLS client certificate authentication (mTLS launcher)
                +
optional leaf-certificate SHA-256 pinning
```

Environment variables:

```text
CRAKBIT_REQUIRE_MTLS=1
CRAKBIT_MTLS_CA=/run/secrets/validator-ca.crt
CRAKBIT_MTLS_CERT=/run/secrets/validator.crt
CRAKBIT_MTLS_KEY=/run/secrets/validator.key
CRAKBIT_PEER_CERT_PINS=/run/secrets/peer-pins.json
CRAKBIT_REQUIRE_PEER_PINS=1
CRAKBIT_PEER_PIN_CACHE_SECONDS=60
```

When mTLS is required, non-HTTPS validator peer URLs are rejected.

### Start a validator with mutual TLS

Use the dedicated launcher so the inbound Uvicorn listener also requires a client certificate:

```bash
python scripts/run_validator_mtls.py \
  --genesis runtime/genesis.json \
  --key runtime/node1/validator.json \
  --data runtime/node1-data \
  --port 9101 \
  --tls-cert /run/secrets/node1.crt \
  --tls-key /run/secrets/node1.key \
  --client-ca /run/secrets/validator-ca.crt \
  --peer-pins /run/secrets/peer-pins.json \
  --require-peer-pins
```

All validator `peer_url` entries in that mTLS network must use `https://` and the certificate SAN must match the hostname used in the URL.

### Certificate fingerprint / pin map

```bash
python scripts/cert_fingerprint.py /run/secrets/node2.crt
```

Pin map:

```json
{
  "crk1VALIDATOR_ADDRESS": "0123456789abcdef...64 hex chars total..."
}
```

The transport layer verifies the normal CA/hostname chain first and then compares the observed leaf certificate SHA-256 to the configured validator-address pin.

Transport status:

```text
GET /transport/status
```

## CLI routing fix

The installed `crakchain` entry point now routes the validator `node` command through the v0.11 application wrapper instead of an older v0.9 application module. This preserves the existing CLI command surface while activating the current RPC/resource-hardening layer.

For an actual mTLS listener, use `scripts/run_validator_mtls.py`; the ordinary `crakchain node` command remains suitable for local/non-mTLS development.

## Fault harness

`blockchain/faults/` contains a Toxiproxy-based development harness for repeatable:

- validator reachability loss,
- latency and jitter,
- downstream timeout,
- recovery after a network fault.

Example:

```bash
cd blockchain/faults
docker compose -f docker-compose.toxiproxy.yml up -d
python control.py setup
python control.py latency validator-2 --ms 1500 --jitter 250
python control.py down validator-4
python control.py reset validator-2
```

This is a transport-fault harness, not proof of Byzantine safety. Consensus-level malicious-message fixtures and long-running multi-host load/partition testing remain open work.

## Validator security runbook

`ops/VALIDATOR_SECURITY_RUNBOOK.md` documents:

- separation of consensus and TLS private keys,
- CA/certificate issuance expectations,
- certificate fingerprint distribution,
- controlled certificate rotation,
- consensus-key compromise response,
- transport-key compromise response,
- incident evidence to retain.

The current pin format uses one expected fingerprint per validator. Automatic dual-pin overlap during certificate rotation is not yet implemented.

## Automated tests

v0.11 adds tests for:

- default transport configuration,
- incomplete mTLS configuration rejection,
- pin-map normalization,
- malformed certificate pin rejection,
- required-pin-map enforcement,
- HTTPS requirement when mTLS policy is enabled.

All earlier consensus, recovery, integrity and resource-limit tests remain in CI.

## Remaining blockers

v0.11 does not make the chain a mainnet candidate. Still required:

1. integrate the execution/state layer with a reviewed BFT consensus core or independently review a complete protocol,
2. implement/test automatic certificate overlap and rotation rather than operator-only coordinated rotation,
3. build archive/history synchronization for snapshot-bootstrapped nodes,
4. add consensus-level Byzantine-message fixtures,
5. run sustained multi-host partition/latency/load/soak experiments,
6. secure monitoring/alert delivery and public RPC reverse proxy/firewall policy,
7. add production-grade secrets/HSM strategy,
8. obtain independent consensus/network/security review.

## Next engineering phase — v0.12

The next phase should focus on **history/archive sync + adversarial multi-host test automation + consensus/execution separation groundwork**, while keeping the production BFT migration decision from ADR-0001 as a hard release gate.
