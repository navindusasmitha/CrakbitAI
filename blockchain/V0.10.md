# Crakbit Chain v0.10 Alpha — Bounded RPC, Recovery Drills & Testnet Operator Hardening

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.10 hardens the operational edge of the development network. It adds explicit request/mempool bounds, a local public-transaction rate limiter, restore-drill tooling, Prometheus alert rules and a reproducible validator deployment scaffold for future public-testnet experiments.

This phase deliberately does **not** claim that the unresolved consensus or validator-transport blockers are solved. The current conservative cross-round lock and the lack of a reviewed native mTLS/certificate lifecycle remain major blockers.

## What v0.10 Adds

### Bounded public/internal request sizes

The active node exposes configurable development limits:

```text
CRAKBIT_MAX_PUBLIC_BODY_BYTES=262144
CRAKBIT_MAX_INTERNAL_BODY_BYTES=2097152
CRAKBIT_PUBLIC_TX_RPM=60
CRAKBIT_MAX_MEMPOOL_TXS=5000
CRAKBIT_MAX_BLOCK_TXS=1000
CRAKBIT_MAX_TX_BYTES=65536
```

Requests with an announced `Content-Length` above the configured endpoint class limit are rejected with HTTP `413`.

The built-in request-size layer is defense-in-depth only. Public deployments must additionally enforce request and connection limits at a reverse proxy/load balancer, including controls for chunked transfer and slow-client behavior.

### Public transaction rate limiting

`POST /transactions` is rate-limited per direct client IP with a process-local fixed one-minute window. The default is 60 requests/minute.

When the limit is exceeded the node returns HTTP `429` with `Retry-After: 60`.

This limiter is intentionally small and local. It is not distributed DDoS protection and it does not trust forwarded headers by default.

### Bounded mempool and block selection

Transaction admission now enforces:

- maximum serialized transaction size,
- maximum pending mempool transaction count,
- existing one-pending-transaction-per-sender behavior.

Block transaction selection is capped separately so an operator can keep block construction work bounded during load testing.

Operational visibility:

```text
GET /limits/status
GET /operations/status
```

### Backup restore drill

v0.9 added verified online backups. v0.10 adds a dedicated restore-drill script that:

1. verifies the backup file and manifest,
2. requires a fresh target directory,
3. copies the SQLite backup into the drill directory,
4. reopens it using the configured genesis,
5. runs full ledger/history/certificate integrity verification,
6. reports the restored height and tip.

Example:

```bash
python scripts/backup_restore_drill.py \
  --genesis runtime/genesis.json \
  --backup runtime/backups/node1.sqlite3 \
  --manifest runtime/backups/node1.sqlite3.manifest.json \
  --output-data runtime/restore-drill/node1
```

The drill never replaces a live database automatically.

### Prometheus alert rules

`blockchain/ops/alerts.yml` adds development alerts for:

- validator scrape loss,
- healthy validator views below the local 3-of-4 quorum,
- authenticated validator views below quorum,
- sustained high consensus rounds,
- sustained mempool pressure,
- newly observed equivocation evidence.

The observability compose file now mounts the rule file into Prometheus.

### Future public-testnet validator scaffold

`blockchain/deploy/testnet/` contains:

- a one-validator-per-host Docker Compose template,
- environment examples for RPC/mempool limits,
- operator guidance that keeps private keys out of the repository,
- explicit HTTPS peer-URL enforcement,
- warnings not to publish the validator RPC directly to the Internet.

The template is intentionally incomplete as a production deployment. Native mTLS provisioning, certificate pinning/rotation and reviewed consensus safety are still required.

## Test Coverage

v0.10 adds automated tests for:

- fixed-window rate-limit behavior,
- invalid limit configuration,
- mempool capacity enforcement,
- serialized transaction-size enforcement.

Existing blockchain CI continues to run all earlier consensus, authentication, recovery and integrity tests.

## Security Boundaries

v0.10 improves resource-bounding and operator recovery practice, but it does not make the chain safe for real value.

Still outstanding:

- mature proof-based cross-round BFT lock/unlock semantics or migration to a reviewed BFT core,
- formal safety/liveness analysis,
- mutually authenticated encrypted validator transport,
- certificate pinning and rotation,
- archive/history synchronization for snapshot-bootstrapped nodes,
- long-running partition/latency/Byzantine/load testing,
- production secret/key management,
- production firewall/reverse-proxy/DDoS architecture,
- independent consensus/network/security audit.

## Next Engineering Phase — v0.11

1. Make the consensus decision: implement a reviewed proof-based BFT lock/unlock protocol or migrate the execution/state layer to an established BFT consensus core.

4. Add archive/history synchronization for snapshot-bootstrapped nodes.
5. Add authenticated monitoring access and alert routing.
6. Add stronger reverse-proxy/network policy examples for public testnet hosts.
7. Add validator key-management, rotation and incident-response runbooks.
