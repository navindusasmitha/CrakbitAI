# Crakbit Chain v0.27 Alpha — Final Mainnet-Candidate Policy

**Package:** `0.27.0a1`  
**Consensus candidate:** CometBFT `v0.40.0`  
**Governed execution:** `crakbit-execution/3`  
**Status:** final mainnet-candidate policy/evidence tooling — **not production mainnet**.

Production CRKBIT has **not launched**. There is no official CRKBIT presale or production token contract. A passing v0.27 gate does not start a network, mint value, authorize custody of real funds, or replace independent operations/security/economic/legal review.

## Purpose

v0.27 defines the last evidence/policy layer before a production-mainnet launch could even be considered. It consumes the operational and review artifacts created by v0.24–v0.26, then adds coordinated upgrade policy, conservative governance timelocks, a frozen economics/genesis parameter set, independent economic/legal attestations, multi-party release approval and a signed final candidate report.

The implementation deliberately distinguishes **mainnet-candidate gate satisfied** from **production mainnet ready/launched**. Every v0.27 artifact keeps `production_mainnet_ready=false` and `production_mainnet_launched=false`.

## What v0.27 adds

- package/CLI `0.27.0a1`,
- signed coordinated upgrade plan with exact source/version/schema binding,
- strict `>2/3` validator readiness threshold before modeled activation,
- explicit migration + rollback artifact hashes and rollback deadline,
- signed governance policy with normal/emergency timelocks and pre-activation cancellation,
- emergency actions still require strict `>2/3` approval,
- emergency policy may not authorize minting or arbitrary user-balance reassignment,
- signed economics/genesis parameter freeze,
- CRKBIT symbol/decimals/supply/fee/incentive/distribution commitment binding,
- explicit no-investment-return/no-token-sale-authorization claims,
- signed external economic-security and legal/regulatory review attestations,
- exact binding of those reviews to the economics freeze and candidate source commit,
- deterministic final candidate identity hash,
- multi-party release approvals with unique signer/approver requirements,
- minimum three distinct release approvals,
- final candidate gate consuming operational readiness + v0.26 remediation gate + governance + economics + external reviews + upgrade plan + release approvals,
- signed final readiness report,
- regression tests for the strict supermajority, exact review binding and multi-party release gate.

## 1. Coordinated upgrade policy

Example:

```bash
crakchain upgrade-plan-v27-build \
  --key private/upgrade-policy-key.json \
  --source-commit EXACT_CANDIDATE_COMMIT \
  --from-package 0.26.0a1 \
  --to-package 0.27.0a1 \
  --from-schema 21 \
  --to-schema 21 \
  --activation-height 250000 \
  --rollback-deadline-height 250500 \
  --migration-artifact-sha256 MIGRATION_SHA256 \
  --rollback-artifact-sha256 ROLLBACK_SHA256 \
  --minimum-ready-validators 3 \
  --total-validators 4 \
  --output runtime/final/upgrade-plan-v27.json
```

The tool refuses thresholds that are not strict `>2/3`. The plan is evidence/policy only and does not automatically mutate a running network.

## 2. Governance timelock policy

```bash
crakchain governance-policy-v27-build \
  --key private/governance-policy-key.json \
  --source-commit EXACT_CANDIDATE_COMMIT \
  --normal-timelock-blocks 100 \
  --emergency-timelock-blocks 10 \
  --cancel-until-blocks-before-activation 5 \
  --emergency-approval-numerator 3 \
  --emergency-approval-denominator 4 \
  --output runtime/final/governance-policy-v27.json
```

The v0.27 policy is intentionally conservative. Emergency governance is still delayed and still requires a strict supermajority. Supply changes require a separate economics review path.

## 3. Freeze economics parameters

The economics input is explicit JSON; v0.27 does not invent final parameters.

Example shape:

```json
{
  "symbol": "CRKBIT",
  "decimals": 8,
  "max_supply_atomic": 2100000000000000,
  "initial_supply_atomic": 2100000000000000,
  "minimum_fee_atomic": 1,
  "validator_incentive_model": "candidate-policy-description",
  "distribution_commitment_sha256": "REPLACE_WITH_64_HEX_SHA256"
}
```

Build the signed freeze:

```bash
crakchain economics-freeze-v27-build \
  --key private/economics-freeze-key.json \
  --source-commit EXACT_CANDIDATE_COMMIT \
  --application-genesis-sha256 APP_GENESIS_SHA256 \
  --consensus-genesis-sha256 CONSENSUS_GENESIS_SHA256 \
  --parameters private/economics.json \
  --output runtime/final/economics-freeze-v27.json
```

The current 21,000,000 / 8-decimal values remain development proposals unless independently reviewed and intentionally frozen by the project. The artifact explicitly does not promise investment returns and does not authorize a token sale.

## 4. Independent economic and legal attestations

Economic-security review example:

```bash
crakchain external-review-v27-build \
  --key reviewer/economic-review-key.json \
  --kind economic-security \
  --reviewer "Independent Economic Reviewer" \
  --source-commit EXACT_CANDIDATE_COMMIT \
  --subject-sha256 ECONOMICS_FREEZE_MANIFEST_SHA256 \
  --decision passed \
  --scope supply \
  --scope fees \
  --scope validator-incentives \
  --output runtime/final/economic-review-v27.json
```

Create a separate `legal-regulatory` attestation using an independently controlled review key. v0.27 requires both review records to target the exact economics-freeze manifest and exact candidate commit.

## 5. Candidate identity and multi-party approvals

Build the deterministic identity from the exact operational/remediation/governance/economics/review/upgrade artifacts:

```bash
crakchain candidate-identity-v27-build \
  --operational-readiness runtime/evidence/readiness-v24.json \
  --remediation-gate runtime/review/remediation-gate-v26.json \
  --governance-policy runtime/final/governance-policy-v27.json \
  --economics-freeze runtime/final/economics-freeze-v27.json \
  --upgrade-plan runtime/final/upgrade-plan-v27.json \
  --economic-review runtime/final/economic-review-v27.json \
  --legal-review runtime/final/legal-review-v27.json \
  --output runtime/final/candidate-identity-v27.json
```

Then at least three distinct release approvers sign that exact identity with separate keys:

```bash
crakchain release-approval-v27-build \
  --key private/release-approver-1.json \
  --approver-id release-approver-1 \
  --role security \
  --source-commit EXACT_CANDIDATE_COMMIT \
  --candidate-identity-sha256 CANDIDATE_IDENTITY_SHA256 \
  --decision approve \
  --output runtime/final/approval-1.json
```

A single release signer is no longer sufficient for the modeled final gate.

## 6. Final candidate gate

```bash
crakchain final-gate-v27-build \
  --identity runtime/final/candidate-identity-v27.json \
  --operational-readiness runtime/evidence/readiness-v24.json \
  --remediation-gate runtime/review/remediation-gate-v26.json \
  --governance-policy runtime/final/governance-policy-v27.json \
  --economics-freeze runtime/final/economics-freeze-v27.json \
  --upgrade-plan runtime/final/upgrade-plan-v27.json \
  --economic-review runtime/final/economic-review-v27.json \
  --legal-review runtime/final/legal-review-v27.json \
  --release-approval runtime/final/approval-1.json \
  --release-approval runtime/final/approval-2.json \
  --release-approval runtime/final/approval-3.json \
  --output runtime/final/final-gate-v27.json
```

The final gate requires:

- `operational_review_candidate=true`,
- v0.26 `refreeze_allowed=true`,
- no unresolved high/critical findings,
- passing governance-policy checks,
- strict-supermajority coordinated upgrade plan,
- passing independent economic-security review,
- passing independent legal/regulatory review,
- at least three unique signed release approvals,
- every release decision set to `approve` for the exact candidate identity.

Even when all checks pass, the result says only `mainnet_candidate_gate_satisfied=true`. It still records `production_mainnet_ready=false`, `production_mainnet_launched=false` and `production_crkbit_launched=false`.

## Security and custody boundary

- Keep validator, governance, review, economics, release-approval and wallet keys separated.
- Do not commit signing private keys or provider credentials.
- Review signatures are evidence of who signed a statement; they are not automatically proof of the reviewer’s independence or real-world process quality.
- Real production launch still requires real independent-host operations, final reviewer corroboration, protected signer/HSM custody, public-edge hardening/capacity, finalized operator procedures and an explicit human launch decision.
- Do not market testnet CRKBIT as a production-value asset.
