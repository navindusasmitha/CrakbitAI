# Crakbit Chain v0.23 Alpha — Public-Testnet Deployment & Operations

**Status:** public-testnet / review-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.23 moves the project from local governed-lab tooling into a repeatable **independent-operator public-testnet deployment and operations workflow**. The implementation creates public validator identities, validates operator/provider/region diversity, builds shared genesis/deployment bundles with no private material, monitors independent nodes, records long-running soak evidence, evaluates explicit launch gates and signs the resulting operational evidence.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Package / CLI

Package version:

```text
0.23.0a1
```

Installed entry point:

```text
crakchain = crakbit_chain.cli_v23:main
```

All v0.22 and earlier governance, migration, state-sync, review and release commands remain available through CLI delegation.

## 2. Public validator identity export

Each validator operator exports only public metadata from their own host:

```bash
crakchain validator-identity-v23-export \
  --home /var/lib/crakbit/cometbft \
  --cometbft /usr/local/bin/cometbft \
  --name validator-1 \
  --operator-id operator-a \
  --provider provider-a \
  --region region-a \
  --p2p-host validator1.example.org \
  --p2p-port 26656 \
  --monitor-rpc-url https://validator1-monitor.example.org \
  --output validator-1-public.json
```

The public identity contains:

- validator/operator name,
- operator/provider/region labels,
- CometBFT node ID,
- CometBFT validator address,
- Ed25519 public key,
- derived `crk1...` application validator address,
- public P2P endpoint,
- monitoring RPC endpoint.

The exporter intentionally excludes validator private keys, seeds, mnemonics, passwords, execution tokens and API secrets.

## 3. Public-testnet inventory

At least four public identities are required:

```bash
crakchain public-testnet-inventory-build \
  --chain-id crakbit-public-testnet-1 \
  --network-name "Crakbit Public Testnet 1" \
  --identity validator-1-public.json \
  --identity validator-2-public.json \
  --identity validator-3-public.json \
  --identity validator-4-public.json \
  --output public-testnet-inventory.json
```

The inventory rejects duplicate names, public keys, node IDs, validator addresses and P2P endpoints. It records explicit diversity gates:

- at least 4 validators,
- at least 4 distinct operator IDs for the independent-operator gate,
- at least 2 providers,
- at least 2 regions.

These are minimum testnet evidence gates, not a guarantee of production decentralization.

## 4. Shared genesis bundle

Given a reviewed CometBFT genesis template and a **public treasury address only**, v0.23 creates matching application and consensus genesis artifacts:

```bash
crakchain public-testnet-genesis-build \
  --inventory public-testnet-inventory.json \
  --cometbft-template cometbft-template-genesis.json \
  --treasury-address crk1PUBLIC_ADDRESS_ONLY \
  --output runtime/public-testnet/genesis
```

Generated files:

```text
application-genesis.json
cometbft-genesis.json
genesis-bundle.json
```

The manifest records SHA-256 hashes and explicitly states:

```text
contains_private_material = false
multi_operator_ceremony_completed = false
independent_review_completed = false
production_mainnet_ready = false
```

Building these files is **not** a substitute for a real multi-operator genesis ceremony.

## 5. Operator deployment bundles

The deployment-bundle generator creates one non-secret package per validator:

```bash
crakchain public-testnet-bundles-build \
  --inventory public-testnet-inventory.json \
  --genesis-bundle runtime/public-testnet/genesis \
  --output runtime/public-testnet/operators
```

Each operator bundle contains:

- shared application genesis,
- shared CometBFT genesis,
- persistent-peer list,
- `node.env.example` containing placeholders only,
- execution-service systemd unit,
- ABCI-bridge systemd unit,
- CometBFT systemd unit,
- operator deployment checklist.

The bundle does **not** contain a validator private key or execution token. Each operator must initialize/protect their own local validator key and generate their execution-service token locally.

Execution port `26659` and ABCI port `26658` should remain loopback/private. Public P2P is separate from operator/management RPC access.

## 6. Independent-node monitoring

One observation:

```bash
crakchain public-testnet-observe \
  --inventory public-testnet-inventory.json \
  --max-height-spread 2 \
  --output runtime/evidence/observation.json
```

The monitor queries each configured monitoring RPC for CometBFT `/status` and `/abci_info` and records:

- node reachability,
- chain/network identity,
- latest heights,
- catching-up status,
- application hash,
- same-height app-hash conflicts,
- height spread,
- monitoring latency.

A non-zero exit is returned when the current observation does not satisfy the configured operational-health conditions.

## 7. Long-running soak evidence

Example 24-hour collection:

```bash
crakchain public-testnet-soak \
  --inventory public-testnet-inventory.json \
  --output runtime/evidence/soak-24h.jsonl \
  --duration-seconds 86400 \
  --interval-seconds 30
```

Summarize:

```bash
crakchain public-testnet-soak-summary \
  --input runtime/evidence/soak-24h.jsonl \
  --output runtime/evidence/soak-24h-summary.json
```

The summary records observed duration, sample count, reachability ratio, health ratio, divergence samples, catching-up samples, maximum height spread and latency statistics.

The minimum v0.23 soak gate requires **actual observed duration >=24 hours**, no same-height application-hash divergence, full reachability and at least 99% healthy observations. Synthetic or shortened evidence must not be represented as a real soak result.

## 8. Public-testnet readiness report

```bash
crakchain public-testnet-readiness \
  --inventory public-testnet-inventory.json \
  --genesis-manifest runtime/public-testnet/genesis/genesis-bundle.json \
  --deployment-manifest runtime/public-testnet/operators/deployment-manifest.json \
  --soak-summary runtime/evidence/soak-24h-summary.json \
  --output runtime/evidence/public-testnet-readiness.json
```

The report distinguishes:

- `public_testnet_launch_candidate`,
- independent-host diversity gate,
- minimum 24-hour soak gate,
- independent security review,
- production-mainnet readiness.

v0.23 always reports:

```text
independent_security_review_completed = false
production_mainnet_ready = false
production_crkbit_launched = false
```

until those external facts actually change in a reviewed future release.

## 9. Signed operations evidence

A dedicated evidence-signing key can sign the exact inventory/readiness/evidence artifact hashes and Git source commit:

```bash
SOURCE_COMMIT=$(git rev-parse HEAD)

crakchain public-testnet-evidence-build \
  --key private/public-testnet-evidence-key.json \
  --source-commit "$SOURCE_COMMIT" \
  --inventory public-testnet-inventory.json \
  --readiness runtime/evidence/public-testnet-readiness.json \
  --artifact runtime/evidence/soak-24h-summary.json \
  --output runtime/evidence/public-testnet-operations-evidence.json
```

Verify:

```bash
crakchain public-testnet-evidence-verify \
  --evidence runtime/evidence/public-testnet-operations-evidence.json \
  --artifact-dir runtime/evidence \
  --expected-source-commit "$SOURCE_COMMIT"
```

The evidence signature authenticates the signer's assertion and bound artifact hashes. It is not an independent security audit.

Never commit/share the evidence signing private key.

## External work still required

v0.23 creates tooling for a real public testnet; it does **not** prove that one has been operated. The following must still be performed and evidenced:

1. provision four or more independently managed VPS validators,
2. verify each operator controls and protects their own validator key,
3. run a real multi-operator genesis ceremony,
4. deploy public RPC/gateway/explorer separately from validator-private services,
5. run 24h, then 72h, then 7-day soak windows,
6. execute validator join/remove/replace campaigns on those independent hosts,
7. run clean-host state-sync and disaster-recovery drills,
8. execute partition, latency, packet-loss, process-kill, disk/storage and sustained-load campaigns,
9. deploy and drill protected remote-signer/HSM-equivalent custody,
10. commission independent consensus/application/governance/network/cryptography/browser-wallet security review,
11. complete production RPC/WAF/DDoS/TLS/secret-management/capacity engineering,
12. finalize validator incentives, production CRKBIT economics and applicable legal/regulatory review.

## Suggested next phase — v0.24

v0.24 should be an **operational fault, recovery and public-testnet hardening phase**:

- operator-safe deployment validation/preflight,
- automated backup/restore and clean-host state-sync drills,
- signed fault-campaign records for restart/partition/latency/packet-loss/load/storage faults,
- validator-governance campaigns across real independent hosts,
- explorer/public-RPC redundancy and recovery checks,
- alert/incident evidence,
- 72-hour and 7-day readiness gates,
- remote-signer/HSM deployment evidence,
- frozen independent-review package after real evidence exists.

Until those external release gates are actually satisfied, describe Crakbit Chain as **public testnet**, **review candidate**, or **mainnet-candidate infrastructure** — not production mainnet.
