# Crakbit Chain v0.14 Alpha — External BFT Bridge, Crash-Safe Commit & Signed Genesis Ceremony

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.14 is the first phase that includes a concrete ABCI bridge toward an established external BFT engine instead of adding more production claims to the bespoke Python consensus. The integration candidate is CometBFT `v0.40.0`, pinned in a separate Go module.

This phase still does **not** claim that a production public Crakbit mainnet exists.

## Major additions

### 1. `crakbit-execution/2` mutating protocol

New module: `crakbit_chain/external_commit.py`

The v2 application protocol adds a staged finalize → atomic commit lifecycle for an external consensus engine.

Application state is kept in a dedicated SQLite database that refuses to mix with the research Python-consensus block database.

The deterministic application hash commits to:

- protocol version,
- chain ID,
- external consensus height,
- external consensus block hash,
- sorted account balances/nonces.

Consensus-local rounds, votes, peer health and monitoring state are excluded.

### 2. Crash-safe staged finalize / commit

`FinalizeBlock`-style requests are persisted before committed state is mutated.

A pending finalize contains:

- height,
- deterministic request hash,
- previous application hash,
- predicted next application hash,
- consensus block hash,
- transaction root/count,
- deterministic fee-pool recipient,
- complete ordered signed transaction batch.

`Commit` revalidates the staged transition and applies all account/transaction/height updates plus the external commit record in a single SQLite transaction.

This provides an all-or-nothing application commit boundary and persistent pending state across application restart.

### 3. Authenticated v0.14 execution service

New service:

```text
crakbit_chain/execution_service_v14.py
scripts/run_execution_service_v14.py
```

Run:

```bash
python scripts/run_execution_service_v14.py \
  --genesis runtime/genesis.json \
  --data runtime/comet-app \
  --token REPLACE_WITH_LONG_RANDOM_SECRET \
  --host 127.0.0.1 \
  --port 26659
```

v2 endpoints:

```text
GET  /v2/info
GET  /v2/pending
POST /v2/check-tx
POST /v2/preview-finalize
POST /v2/finalize
POST /v2/commit
```

All except `/health` require the bearer token.

### 4. Real CometBFT ABCI bridge module

New Go module:

```text
blockchain/cometbft-app/
```

It pins:

```text
github.com/cometbft/cometbft v0.40.0
```

The bridge implements the external BFT application-facing methods needed for the PoC:

- `Info`
- `CheckTx`
- `PrepareProposal`
- `ProcessProposal`
- `FinalizeBlock`
- `Commit`
- minimal `/app/info` query support

The default bridge socket is loopback `tcp://127.0.0.1:26658`. It forwards application operations to the authenticated Python execution service on loopback HTTP.

Build/test:

```bash
cd blockchain/cometbft-app
go mod download
go test -mod=mod ./...
go build -o crakbit-cometbft-bridge .
```

### 5. Signed genesis ceremony

New module: `crakbit_chain/genesis_ceremony.py`

New CLI commands:

```bash
crakchain ceremony-create --genesis runtime/genesis.json --output runtime/ceremony.json
crakchain ceremony-sign --ceremony runtime/ceremony.json --key runtime/node1/validator.json
crakchain ceremony-verify --ceremony runtime/ceremony.json --genesis runtime/genesis.json
```

The ceremony statement commits to:

- exact genesis SHA-256,
- genesis fingerprint,
- chain/network identity,
- complete validator public identity list,
- validator count,
- strict >2/3 quorum threshold.

Only configured validator keys can attest. Verification rejects duplicate, unknown, mismatched or invalid signatures and requires quorum by default.

This is a testnet integrity ceremony. Validator private keys must never be shared or committed.

### 6. New external execution CLI

v0.14 adds local operator/debug commands:

```text
crakchain external-status
crakchain external-preview
crakchain external-finalize
crakchain external-commit
```

Example:

```bash
crakchain external-status \
```

These commands make it possible to test the v2 transition contract independently from CometBFT before a multi-process network is started.

### 7. Node integration visibility

The existing research node now reports:

```text
GET /consensus/integration-status
```

It explicitly distinguishes:

- research Python consensus currently active in that node,
- availability of the external CometBFT bridge,
- pinned CometBFT candidate version,
- external execution protocol version,
- the fact that external BFT is not automatically active inside the research node.

### 8. CI now covers both languages

The blockchain GitHub Actions workflow runs:

- the complete Python pytest suite,
- Go 1.25 setup,
- CometBFT bridge dependency download,
- Go bridge tests.

This keeps the Python state machine and Go ABCI bridge under one change-triggered blockchain CI workflow.

## Design constraints

### Separate consensus keys

CometBFT node/validator keys are separate from Crakbit application keys. Do not reuse Crakbit wallet, faucet, release, TLS or research-validator private keys as CometBFT node credentials.

### Deterministic fee pool

v0.14 parks external-consensus transaction fees in a deterministic test-only application fee-pool address derived from chain ID. Production fee distribution/economics are intentionally not defined here.

### No automatic mainnet migration

The normal `crakchain node` path remains the research Python-consensus node for backwards-compatible local research. The external CometBFT PoC is a separate process topology: CometBFT → Go ABCI bridge → Python v2 execution service → dedicated application DB.

## Remaining blockers

v0.14 is a major integration milestone, not a production release. Remaining blockers include:

1. sustained live multi-process CometBFT replay/restart testing,
2. multi-host validator network deployment and published fault/soak evidence,
3. app-ahead/consensus-ahead recovery testing across every crash point,
4. CometBFT state-sync integration with Crakbit snapshots,
5. validator-set lifecycle/governance design,
6. indexed external-consensus explorer storage,
7. persistent/upstream faucet abuse protection,
8. production key custody/HSM or remote-signer strategy,
9. production monitoring, firewall, reverse-proxy and DDoS architecture,
10. independent consensus/network/application security review.

## Suggested next major phase — v0.15

The next phase should move from an integration bridge to a repeatable multi-process test network:

- add one-command local CometBFT multi-node lab generation,
- generate/verify consensus genesis and peer inventory separately from Crakbit application genesis,
- add crash-point replay test matrix for FinalizeBlock/Commit,
- add external application snapshot/state-sync adapter work,
- add persistent indexed explorer database,
- make faucet rate/distribution limits persistent,
- automate multi-host deployment inventory and health checks,
- run partition/latency/restart/load campaigns,
- publish signed testnet release + ceremony + soak bundle,
- prepare first independent review handoff.
