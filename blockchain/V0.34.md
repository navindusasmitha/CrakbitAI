# Crakbit Chain v0.34 Alpha — PoW Operations / Payout / Reorg Preparation

**Package:** `0.34.0a1`  
**Active devnet consensus:** native Proof of Work  
**Active block algorithm:** `crakpow-scrypt-v1`  
**RandomX:** optional v0.33 candidate; **not active consensus**  
**P2P:** `crakbit-p2p/1`  
**Pool:** `crakbit-pool/2`  
**Status:** multi-node PoW devnet alpha — **not production mainnet**.

Production CRKBIT has not launched. There is no official presale or production token contract.

## Purpose

v0.34 does not silently switch mining algorithms. It adds the operational/accounting pieces needed before a serious public PoW testnet: signed benchmark evidence, an explicit human algorithm-decision record, UTXO undo metadata, persistent peer selection tooling, PoW statistics/confirmation helpers, watch-only records and mature-coinbase-aware pool payout planning/reconciliation.

## Implemented

- signed per-machine scrypt/RandomX benchmark evidence format,
- benchmark gate requiring multiple unique machines by default,
- explicit `hold` / `scrypt` / `randomx` human decision record,
- algorithm decision **does not authorize consensus activation**,
- canonical UTXO undo-journal backfill and verification,
- undo records include block-created outpoints plus pre-block UTXOs required for disconnect,
- persistent peer address/reputation database,
- coarse endpoint-diversity selection and temporary failure bans,
- rolling PoW difficulty/hashrate/miner statistics,
- transaction confirmation status,
- mempool-based fee-rate estimate helper,
- watch-only address file with no private key,
- mature coinbase-aware PPLNS payout-plan builder,
- deterministic signed UTXO payout transaction construction from a separate pool hot-wallet key,
- pending payout reservation so the same PPLNS claim is not planned twice,
- manual submit state,
- confirmation-depth reconciliation before PPLNS balances are debited,
- idempotent payout finalization,
- v0.34 regression tests covering these paths.

## Algorithm benchmark gate

A benchmark record is self-attested by a dedicated Ed25519 evidence key. It records machine ID, CPU model, logical threads, RAM, scrypt hashrate and optional RandomX/native-library measurements.

Example:

```powershell
crakchain pow-benchmark-v34-build `
  --key private\bench-key.json `
  --machine-id cpu-lab-01 `
  --cpu-model "YOUR CPU" `
  --logical-threads 12 `
  --ram-mib 16384 `
  --scrypt-hps 123.4 `
  --randomx-hps 456.7 `
  --randomx-mode light `
  --randomx-selftest-passed `
  --output runtime\v34\bench-01.json
```

Aggregate multiple real machines:

```powershell
crakchain pow-benchmark-gate-v34-build `
  --key private\release-evidence.json `
  --record runtime\v34\bench-01.json `
  --record runtime\v34\bench-02.json `
  --output runtime\v34\benchmark-gate.json
```

Then record a human decision:

```powershell
crakchain pow-algorithm-decision-v34-build `
  --key private\release-evidence.json `
  --benchmark-gate runtime\v34\benchmark-gate.json `
  --decision hold `
  --rationale "Need more independent CPU/GPU evidence" `
  --output runtime\v34\algorithm-decision.json
```

Even `--decision randomx` records:

```text
consensus_activation_authorized=false
```

A separate versioned consensus upgrade is required before any algorithm change.

## UTXO undo journal

v0.32 safely reorganizes by replaying a candidate branch and replacing canonical state. v0.34 introduces the data needed for a future efficient disconnect/connect engine without changing live consensus mechanics yet.

```powershell
crakchain pow-undo-v34-backfill `
  --db runtime\node1\chain.sqlite3 `
  --output runtime\v34\undo-backfill.json

crakchain pow-undo-v34-verify `
  --db runtime\node1\chain.sqlite3
```

Each canonical block records:

- outputs created by the block,
- earlier-chain UTXOs spent by the block,
- amount/address/coinbase-height data required to restore those UTXOs,
- a deterministic SHA-256 of the undo manifest.

The current live reorg engine still uses replay/state replacement. v0.34 does **not** claim that incremental undo is active yet.

## Persistent peer book

```powershell
crakchain pow-peer-v34-note `
  --db runtime\node1\peers.sqlite3 `
  --endpoint 203.0.113.10:28444 `
  --success

crakchain pow-peer-v34-select `
  --db runtime\node1\peers.sqlite3 `
  --limit 16 `
  --max-per-bucket 2
```

IPv4 peers are coarsely grouped by `/16`, IPv6 by `/32`, and DNS names by a simple suffix bucket. This reduces accidental concentration but is **not** proof of ASN/operator diversity and is not complete anti-eclipse protection.

## Mature pool payout planning

PPLNS balances are still testnet accounting, but v0.34 adds a guarded path to construct real UTXO payout transactions from **mature** pool-wallet outputs.

```powershell
crakchain pow-payout-v34-build `
  --chain-db runtime\node1\chain.sqlite3 `
  --pool-db runtime\pow-v33\pool.sqlite3 `
  --wallet private\pool-hot-wallet.json `
  --minimum-payout-crk 0.10 `
  --fee-crk 0.0001 `
  --output runtime\v34\payout-plan.json
```

This command builds/signs a transaction but does **not** auto-submit it and does **not** debit miner PPLNS balances.

Export the transaction and submit it through the normal devnet transaction path only after operator review:

```powershell
crakchain pow-payout-v34-export-tx `
  --pool-db runtime\pow-v33\pool.sqlite3 `
  --plan-id PLAN_ID `
  --output runtime\v34\payout-tx.json

crakchain pow-submit-tx-v31 `
  --db runtime\node1\chain.sqlite3 `
  --transaction runtime\v34\payout-tx.json
```

After it is actually submitted:

```powershell
crakchain pow-payout-v34-mark-submitted `
  --pool-db runtime\pow-v33\pool.sqlite3 `
  --plan-id PLAN_ID
```

Only after the transaction is confirmed to the configured depth does reconciliation debit the internal PPLNS balances:

```powershell
crakchain pow-payout-v34-reconcile `
  --chain-db runtime\node1\chain.sqlite3 `
  --pool-db runtime\pow-v33\pool.sqlite3 `
  --plan-id PLAN_ID `
  --minimum-confirmations 2
```

For any future public-value pool, hot/cold key separation, payout limits, compromise response, independent accounting review and external infrastructure hardening remain mandatory.

## Important boundaries

- active consensus is still `crakpow-scrypt-v1`,
- RandomX is not activated,
- stock XMRig live compatibility is not yet claimed,
- v0.34 undo data is prepared/verified but the live reorg engine still uses v0.32 replay replacement,
- peer diversity is coarse, not ASN/operator-proof,
- fee estimation is an alpha mempool heuristic,
- payout plans are operator-controlled and should use a dedicated hot-wallet key,
- production economics are not frozen,
- no production-mainnet or production-CRKBIT launch has occurred.
