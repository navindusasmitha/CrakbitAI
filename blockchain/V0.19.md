# Crakbit Chain v0.19 Alpha — Review Remediation & Reproducible Release Engineering

**Status:** public-testnet / review-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.19 turns the v0.18 review-freeze work into a remediation and release-engineering phase. It adds machine-readable review finding gates, reproducible artifact comparison, a direct-dependency CycloneDX SBOM, signed release provenance and signed operations-drill evidence.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Security-review remediation matrix

New module:

```text
crakbit_chain/review_findings.py
```

CLI:

```text
crakchain review-findings-build
crakchain review-findings-check
```

Input review files may contain either a JSON list or:

```json
{
  "findings": [
    {
      "id": "SEC-001",
      "title": "Example finding",
      "severity": "high",
      "status": "remediated",
      "regression_tests": ["tests/test_sec_001.py"],
      "evidence": ["evidence/sec-001.json"]
    }
  ]
}
```

Supported severities are `info`, `low`, `medium`, `high`, and `critical`. Supported statuses are `open`, `accepted`, `remediated`, and `not_applicable`.

The v0.19 release gate remains conservative:

- unresolved `high` or `critical` findings block the gate,
- `accepted` high/critical risk still blocks the automated gate,
- remediated high/critical findings require at least one recorded regression-test reference,
- clearing this matrix does **not** claim production-mainnet readiness.

## 2. Reproducible artifact comparison

New module:

```text
crakbit_chain/reproducible_build.py
```

CLI:

```text
crakchain repro-compare
```

The command compares explicitly selected build artifacts from two build roots by exact file size and SHA-256. CI now performs:

- two Python wheel builds under a fixed `SOURCE_DATE_EPOCH`,
- two Go bridge builds with `-trimpath -buildvcs=false`,
- SHA-256 equality checks through the same v0.19 command.

Matching outputs show that the supplied artifacts are byte-identical in that build environment. They do not by themselves prove independent build-environment diversity or a completed supply-chain audit.

## 3. Direct-dependency CycloneDX SBOM

New module:

```text
crakbit_chain/sbom_v19.py
```

CLI:

```text
crakchain sbom-build
```

The generated CycloneDX 1.5 JSON records:

- direct Python runtime dependencies from `pyproject.toml`,
- installed Python versions when available,
- direct Go requirements from `cometbft-app/go.mod`,
- SHA-256 fingerprints for `pyproject.toml`, `go.mod`, and `go.sum` when present.

The SBOM explicitly records that it is **not yet a complete transitive dependency inventory**. A production release process should generate and independently validate a complete transitive SBOM for the exact release environment.

## 4. Signed release provenance

New module:

```text
crakbit_chain/release_provenance_v19.py
```

CLI:

```text
crakchain release-provenance-build
crakchain release-provenance-verify
```

A signed provenance manifest binds:

- exact Git source commit,
- package version,
- declared CometBFT version,
- chain ID and genesis fingerprint,
- exact genesis-file SHA-256,
- operator-selected release artifact hashes,
- optional SBOM hash,
- optional reproducibility-report hash,
- dedicated Ed25519 release signer identity.

The manifest never upgrades itself into an audit certificate. It always keeps:

```text
independent_security_review_completed = false
production_mainnet_ready = false
production_crkbit_launched = false
```

unless a future, separately reviewed release process defines stronger semantics.

## 5. Signed operations-drill evidence

New module:

```text
crakbit_chain/ops_drill_evidence.py
```

CLI:

```text
crakchain ops-drill-build
crakchain ops-drill-verify
```

Supported drill categories:

- `upgrade`,
- `rollback`,
- `incident-response`,
- `disaster-recovery`,
- `validator-lifecycle`.

The format binds exact source commit, operator-reported timing/result, summary text, evidence-file hashes and a dedicated Ed25519 signer.

It deliberately distinguishes **operator-reported success** from independent verification. Recording a drill artifact does not claim that an HSM, external auditor, independent provider or production network was involved.

## 6. CI release-engineering evidence

The blockchain GitHub Actions workflow now runs:

1. Python tests,
2. CometBFT Go bridge tests,
3. two Python wheel builds and byte-for-byte comparison,
4. two Go bridge builds and byte-for-byte comparison,
5. direct-dependency CycloneDX SBOM generation,
6. upload of test/reproducibility/SBOM evidence artifacts.

This makes release-engineering regressions visible in CI rather than relying only on local operator steps.

## 7. Example release-candidate flow

```bash
# exact source
SOURCE_COMMIT=$(git rev-parse HEAD)

# direct-dependency SBOM
crakchain sbom-build \
  --repo-root .. \
  --output runtime/release/sbom.cdx.json

# security review matrix
crakchain review-findings-build \
  --source-commit "$SOURCE_COMMIT" \
  --finding private/review-findings.json \
  --output runtime/review/remediation-matrix.json

crakchain review-findings-check \
  --matrix runtime/review/remediation-matrix.json

# signed release provenance after real artifacts exist
crakchain release-provenance-build \
  --genesis runtime/genesis.json \
  --key private/release-signing-key.json \
  --source-commit "$SOURCE_COMMIT" \
  --package-version 0.19.0a1 \
  --cometbft-version v0.40.0 \
  --sbom runtime/release/sbom.cdx.json \
  --repro-report runtime/release/reproducible-build.json \
  --output runtime/release/provenance.json
```

Never commit release/review/validator/wallet private keys.

## External gates still open

Repository work cannot honestly complete the following external requirements by itself:

1. sustained four-validator operation across independently managed hosts/providers,
2. published live clean-host state-sync evidence,
3. real partition/packet-loss/latency/process-kill/load campaigns,
4. deployed and drilled remote-signer/HSM-equivalent validator custody,
5. multi-operator genesis ceremony with independently held keys,
6. independent consensus/application/network/browser-wallet security review,
7. complete transitive SBOM/supply-chain review,
8. production multi-edge DDoS/WAF/capacity engineering,
9. finalized validator economics/incentives and applicable legal/regulatory review.

## Suggested next phase — v0.20

v0.20 should focus on **upgrade compatibility and controlled validator lifecycle**, not on pretending the open external gates are complete:

- versioned application database migrations,
- offline migration dry-run and rollback verification,
- protocol compatibility matrix,
- validator-set update application boundary,
- safe join/remove/replace testnet drills,
- historical state/index migration verification,
- signed migration/rollback evidence,
- release-candidate hardening from any real review findings.

Until the external gates are satisfied, use **public testnet**, **review candidate**, or **mainnet-candidate infrastructure** — not production mainnet.
