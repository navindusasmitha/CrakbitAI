# Crakbit Chain v0.24 Alpha — Operational Fault / Recovery Hardening

**Package:** `0.24.0a1`  
**Consensus candidate:** CometBFT `v0.40.0`  
**Governed execution:** `crakbit-execution/3`  
**Status:** public-testnet / operational-review-candidate tooling — **not production mainnet**.

Production CRKBIT has **not launched**. There is no official CRKBIT presale or production token contract. This software must not be represented as ready for custody of real value.

## Purpose

v0.23 added tooling to assemble an independent-operator public testnet. v0.24 hardens the operational evidence boundary: a node can be checked before start, faults must have explicit recovery actions, recovery/state-sync results can be recorded deterministically, public RPC/explorer redundancy can be tested, protected-signer drills can be recorded without private-key material, and 24-hour / 72-hour / 7-day soak gates are kept separate.

The phase intentionally does **not** manufacture operational results. A generated record is only evidence of the inputs supplied to it; real gates remain false until real independent-host tests are performed.

## What v0.24 adds

- package/CLI `0.24.0a1`,
- operator-safe host preflight,
- exact package / CometBFT / application-genesis / consensus-genesis identity checks,
- loopback-only execution/ABCI preflight gates,
- token-presence check that never reads or emits the token value,
- writable-data-directory and minimum-free-space checks,
- typed fault plans for restart, process-kill, partition, latency, packet-loss, sustained load and storage faults,
- mandatory recovery command for every planned fault,
- explicit conversion of executed fault-campaign output into recovery-aware evidence,
- backup/restore and clean-host state-sync recovery records,
- protected remote-signer/HSM-style drill records with explicit no-key-export gate,
- public RPC + explorer redundancy evaluator,
- same-height application-hash divergence detection across redundant RPC endpoints,
- separate 24-hour, 72-hour and 7-day soak gates,
- aggregate operational-review-candidate readiness report,
- signed v0.24 operations evidence bound to an exact Git commit and SHA-256 artifact hashes,
- regression tests for the above safety properties.

## Host preflight

Run this on each validator host before enabling services:

```bash
crakchain host-preflight-v24 \
  --node-name validator-1 \
  --application-genesis /etc/crakbit/application-genesis.json \
  --application-genesis-sha256 EXPECTED_APP_GENESIS_SHA256 \
  --consensus-genesis /var/lib/crakbit/cometbft/config/genesis.json \
  --consensus-genesis-sha256 EXPECTED_COMET_GENESIS_SHA256 \
  --data /var/lib/crakbit/app \
  --token-file /etc/crakbit/node.env \
  --execution-bind 127.0.0.1:26659 \
  --abci-bind tcp://127.0.0.1:26658 \
  --cometbft /usr/local/bin/cometbft \
  --expected-cometbft-version v0.40.0 \
  --output runtime/evidence/validator-1-preflight.json
```

The preflight records only whether the token file exists. It does not read, print or sign the execution token.

## Fault campaigns

v0.24 separates **planning** from **execution**. The plan format requires a recovery command for every fault and remains dry-run by default. A plan does not execute anything.

Example plan spec:

```json
{
  "name": "validator restart campaign",
  "steps": [
    {
      "name": "restart-validator-2",
      "kind": "restart",
      "target": "validator-2",
      "command": ["systemctl", "restart", "crakbit-cometbft"],
      "recovery_command": ["systemctl", "start", "crakbit-cometbft"],
      "expected_impact": "validator temporarily unavailable, chain continues with quorum"
    }
  ]
}
```

Build it:

```bash
crakchain fault-v24-plan-build \
  --spec private/restart-plan-spec.json \
  --output runtime/evidence/restart-plan.json
```

Existing `scripts/run_fault_campaign.py` remains the execution tool and still requires explicit `--execute`. Do not run destructive network/storage commands against systems you do not own or administer. After a real authorized campaign, normalize the result:

```bash
crakchain fault-v24-result-build \
  --plan runtime/evidence/restart-plan.json \
  --campaign-result runtime/evidence/restart-raw.json \
  --output runtime/evidence/restart-result.json
```

## Recovery records

A backup restore only passes when height, application hash and optional state root match the source identity. Clean-host state sync additionally requires the operator to assert that the destination was a clean host.

```bash
crakchain recovery-v24-record \
  --kind clean-host-state-sync \
  --source-height 120000 \
  --restored-height 120000 \
  --source-app-hash EXPECTED_APP_HASH \
  --restored-app-hash RESTORED_APP_HASH \
  --clean-host \
  --output runtime/evidence/clean-host-state-sync.json
```

This record does not by itself prove independent execution; raw state-sync/backup logs should be included in the signed evidence set.

## Remote signer / HSM evidence

```bash
crakchain remote-signer-v24-record \
  --validator validator-1 \
  --signer-type hsm-backed-remote-signer \
  --double-sign-protection \
  --restart-recovery-drilled \
  --failover-drilled \
  --signer-endpoint-private \
  --output runtime/evidence/validator-1-signer.json
```

Do **not** pass `--key-exported` for a protected deployment. The record never contains a private key. It is an operator record, not an independent HSM certification.

## RPC / explorer redundancy

```bash
crakchain redundancy-v24-check \
  --chain-id crakbit-public-testnet \
  --rpc https://rpc1.example.test \
  --rpc https://rpc2.example.test \
  --explorer https://index1.example.test \
  --explorer https://index2.example.test \
  --output runtime/evidence/redundancy.json
```

The RPC gate requires at least two reachable RPC endpoints, expected chain identity and no same-height application-hash conflict. Explorer redundancy requires at least two reachable explorer health endpoints.

## 24h / 72h / 7d readiness

Use actual `public-testnet-soak-summary` artifacts from real elapsed runs. Do not synthesize timestamps or shorten a run and label it as a longer soak.

```bash
crakchain readiness-v24-build \
  --soak-24h runtime/evidence/soak-24h-summary.json \
  --soak-72h runtime/evidence/soak-72h-summary.json \
  --soak-7d runtime/evidence/soak-7d-summary.json \
  --fault-result runtime/evidence/fault-restart.json \
  --fault-result runtime/evidence/fault-process-kill.json \
  --fault-result runtime/evidence/fault-partition.json \
  --fault-result runtime/evidence/fault-latency.json \
  --fault-result runtime/evidence/fault-packet-loss.json \
  --fault-result runtime/evidence/fault-load.json \
  --fault-result runtime/evidence/fault-storage.json \
  --recovery runtime/evidence/backup-restore.json \
  --recovery runtime/evidence/clean-host-state-sync.json \
  --signer-record runtime/evidence/validator-1-signer.json \
  --redundancy runtime/evidence/redundancy.json \
  --output runtime/evidence/v24-readiness.json
```

`operational_review_candidate` becomes true only when all modeled gates are supplied and pass. Even then, `independent_security_review_completed`, `production_mainnet_ready` and `production_crkbit_launched` remain false by design.

## Signed evidence

Use a dedicated operations-evidence signing key, separate from validator/wallet/TLS/release keys:

```bash
SOURCE_COMMIT=$(git rev-parse HEAD)

crakchain ops-v24-sign \
  --key private/operations-evidence-key.json \
  --source-commit "$SOURCE_COMMIT" \
  --package-version 0.24.0a1 \
  --cometbft-version v0.40.0 \
  --artifact runtime/evidence/v24-readiness.json \
  --artifact runtime/evidence/redundancy.json \
  --artifact runtime/evidence/backup-restore.json \
  --output runtime/evidence/v24-operations-evidence.json
```

A valid signature proves that the signer bound itself to those exact bytes. It does **not** convert operator-generated artifacts into an independent security audit.

## What still blocks production mainnet

v0.24 adds the machinery needed to collect stronger operational evidence. The following still have to happen in reality: four or more independently managed validators, genuine multi-operator genesis ceremony, real 24h/72h/7d operation, real fault/load/storage/state-sync campaigns, protected signer deployment, production multi-edge RPC/WAF/DDoS/TLS/secret-management engineering, independent consensus/application/governance/network/cryptography/browser-wallet review, finalized validator/CRKBIT economics and applicable legal/regulatory review.

Until those gates are independently reviewable, describe Crakbit Chain as a **public-testnet / review-candidate project**, not a production mainnet.
