# Crakbit Chain v0.6 Alpha — Authenticated Peers & Signed Snapshot Foundation

**Status:** development/research alpha. Not a production mainnet.

v0.6 hardens the validator-network boundary around the existing v0.5 prevote/precommit consensus prototype. It does **not** claim production Byzantine-fault tolerance or production transport security.

## Implemented in v0.6

### Ed25519-authenticated internal validator requests

Every `/internal/*` validator request made by the v0.6 node carries:

- validator address,
- millisecond timestamp,
- random nonce,
- Ed25519 signature.

The signed payload commits to:

```text
HTTP method
request path
SHA-256(request body)
validator address
timestamp
nonce
```

The receiver verifies that the signer is a configured genesis validator, checks the signature, enforces a bounded timestamp window and rejects repeated nonces during the active process replay window.

This protects consensus-object requests from unauthenticated callers and detects body tampering. It is **application-level authentication**, not encryption.

### Validator identity challenge/response

`POST /internal/hello` provides a signed challenge/response identity handshake. Peer-health checks use this handshake before recording a peer as an authenticated validator identity.

The handshake binds:

```text
chain_id
validator address
validator public key
caller challenge
timestamp
```

### Optional HTTPS enforcement mode

Validators can be started with:

```bash
crakchain node ... --require-peer-tls
```

or:

```bash
CRAKBIT_REQUIRE_PEER_TLS=1
```

When enabled, configured remote validator peer URLs must use `https://`.

This mode **does not provision certificates or TLS automatically**. Operators are responsible for a reviewed TLS/mTLS/reverse-proxy deployment and certificate lifecycle. The default local Docker devnet intentionally continues to use isolated HTTP networking for development.

### Signed state snapshot export

`GET /snapshot/latest` returns a validator-signed snapshot envelope containing:

- chain ID,
- genesis fingerprint,
- finalized height,
- finalized block hash,
- sorted account balances/nonces,
- deterministic accounts root,
- snapshot hash,
- validator signer identity and signature.

A snapshot can be verified with:

```bash
crakchain snapshot-verify --snapshot snapshot.json --genesis runtime/genesis.json
```

v0.6 provides **snapshot generation and verification only**. It does not yet trustlessly import a snapshot or implement production fast state sync.

### Prometheus-style development metrics

In addition to the existing JSON `/metrics` endpoint, v0.6 exposes:

```text
GET /metrics/prometheus
```

with development gauges/counters for chain height, consensus round, mempool size, local prevote/precommit records, lock state, evidence/events and authenticated/healthy validator views.

## Consensus

The v0.5 consensus flow remains:

```text
proposal
  -> >2/3 prevote certificate
  -> >2/3 precommit certificate
  -> finalization
```

Certified view changes remain required for later rounds. v0.6 does not change the conservative lock/unlock semantics.

## Important limitations

- The v0.5/v0.6 consensus lock still lacks a mature proof-based cross-round unlock rule.
- Replay-nonce memory for HTTP peer authentication is process-local; timestamp bounds reduce but do not eliminate restart-window replay concerns.
- Local Docker networking is not encrypted by default.
- `--require-peer-tls` only enforces HTTPS URLs; it does not implement certificate issuance, mTLS or rotation.
- Peer status telemetry after the identity handshake is still fetched from a public status endpoint and should be treated as operational data, not signed consensus evidence.
- Signed snapshots are export/verification artifacts; fast-sync import is not implemented.
- No staking, slashing, validator-set changes or production governance exists.
- No independent security audit has been completed.

## v0.7 priorities

1. Review or replace the conservative cross-round lock with a mature proof-based unlock/BFT design.
2. Move from signed HTTP requests toward a reviewed mutually authenticated encrypted validator transport.
3. Persist/reconcile peer-session replay state or use a transport/session protocol with stronger replay guarantees.
4. Add snapshot quorum/certification and verified snapshot import / fast state sync.
5. Add database corruption, crash and restart recovery tests.
6. Run long-lived validator partition, latency, Byzantine-behavior and load tests.
7. Add production-oriented Prometheus/Grafana deployment examples and alert rules.
8. Build public-testnet infrastructure, faucet abuse controls and operator runbooks.
9. Obtain independent consensus/network security review before any real-value use.
