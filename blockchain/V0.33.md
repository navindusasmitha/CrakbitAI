# Crakbit Chain v0.33 Alpha — CPU Mining / RandomX Candidate / Pool Hardening

**Package:** `0.33.0a1`  
**Active devnet consensus:** native Proof of Work  
**Active block algorithm:** `crakpow-scrypt-v1`  
**RandomX candidate:** `crakpow-randomx-v1-candidate` (optional native adapter; **not consensus-enabled**)  
**P2P protocol:** `crakbit-p2p/1`  
**Pool protocol:** `crakbit-pool/2`  
**Status:** multi-node PoW devnet alpha — **not production mainnet**.

Production CRKBIT has not launched. There is no official presale or production token contract. Do not use this alpha to custody real value.

## Why v0.33 exists

v0.31 introduced real CPU-mined blocks and v0.32 added P2P fork/reorg behavior. v0.33 focuses on the mining side without silently replacing consensus with an unreviewed algorithm.

The existing scrypt chain remains the active devnet consensus path. RandomX is integrated as a real optional native candidate so it can be built, self-tested, benchmarked and exercised against XMRig-style job/submit structures before any future activation decision.

## Implemented

- optional ctypes binding to upstream RandomX `v1.1.8`,
- upstream official API-example self-test vector,
- RandomX light mode and fast/full-dataset mode,
- explicit upstream library discovery through `CRAKBIT_RANDOMX_LIBRARY`,
- deterministic candidate key-block schedule (`2048` interval / `64` block delay),
- fixed candidate hashing blob with XMRig default RandomX nonce offset at byte `39`,
- candidate XMRig `rx/0` job builder,
- candidate XMRig submit/hash verifier using the native RandomX library,
- deterministic v0.33 algorithm/interoperability vectors,
- Windows helper that builds pinned upstream RandomX as a shared library,
- multi-thread CPU miner for the active scrypt PoW RPC,
- multi-thread native pool miner,
- `crakbit-pool/2` hardened pool path,
- per-worker variable difficulty (vardiff),
- stale-job rejection,
- duplicate/replayed share rejection,
- connection message-rate limits,
- optional TLS 1.2+ for the native pool,
- optional pool authorization token,
- pool statistics for accepted shares/workers/rounds/balances,
- regression tests that do not require RandomX to be installed in CI.

## RandomX candidate boundary

RandomX upstream is written in C++ and exposes a C API. v0.33 does **not** vendor a prebuilt binary and does not download one at runtime. Operators build the pinned source and point the runtime at the resulting shared library.

Windows helper:

```powershell
cd blockchain
.\scripts\build_randomx_v33.ps1
```

Then set the path printed by the script:

```powershell
$env:CRAKBIT_RANDOMX_LIBRARY="C:\path\to\randomx.dll"
```

Check availability:

```powershell
crakchain pow-randomx-v33-info
```

Run the upstream example self-test:

```powershell
crakchain pow-randomx-v33-selftest --mode light
```

Benchmark light mode:

```powershell
crakchain pow-randomx-v33-benchmark --mode light --seconds 5
```

Fast mode can require roughly the upstream full RandomX dataset memory footprint and should only be used on a machine with enough RAM:

```powershell
crakchain pow-randomx-v33-benchmark --mode fast --seconds 5
```

## RandomX key schedule candidate

The candidate schedule follows the upstream recommended pattern rather than allowing a miner to choose the RandomX key.

For candidate height `H`:

```text
if H < 64:
    key_height = 0
else:
    key_height = floor((H - 64) / 2048) * 2048
```

Example:

```powershell
crakchain pow-randomx-v33-key-height --height 2112
```

returns key block height `2048`.

This is **candidate policy only**. It is not active in v0.33 block validation.

## Deterministic candidate vectors

```powershell
crakchain pow-randomx-v33-vectors `
  --output runtime\v33\randomx-vectors.json
```

The file records the candidate blob layout, nonce offset, key schedule and upstream self-test vector without enabling RandomX consensus.

## Multi-thread CPU solo mining

Run a v0.32 node normally, then point the v0.33 miner at its RPC:

```powershell
crakchain pow-mine-v33-rpc `
  --node-url http://127.0.0.1:28443 `
  --miner-address crk1YOUR_ADDRESS `
  --threads 8 `
  --blocks 1
```

The workers scan disjoint nonce sequences and the node still independently validates every submitted block.

## Hardened first-party pool

Start the v0.33 pool:

```powershell
crakchain pow-pool-v33-run `
  --db runtime\pow-v33\pool.sqlite3 `
  --node-url http://127.0.0.1:28443 `
  --pool-address crk1POOL_ADDRESS `
  --host 0.0.0.0 `
  --port 3333 `
  --vardiff-target-seconds 15 `
  --stale-job-seconds 120
```

Run the multi-thread native miner:

```powershell
python scripts\run_pow_pool_miner_v33.py `
  --host 127.0.0.1 `
  --port 3333 `
  --address crk1MINER_ADDRESS `
  --worker cpu-01 `
  --threads 8
```

Pool protections added in v0.33:

- a `(job_id, extra_nonce, nonce)` submission can only be credited once,
- the same share hash cannot be credited twice for a job,
- expired work is rejected,
- each worker gets an adaptive share target,
- inbound connection messages are rate limited,
- TLS and an optional shared authorization token can be enabled.

A production public pool still requires reverse-proxy/DDoS engineering, monitoring, payout reconciliation and independent accounting/security review.

## TLS example

```powershell
crakchain pow-pool-v33-run `
  --db runtime\pow-v33\pool.sqlite3 `
  --node-url http://127.0.0.1:28443 `
  --pool-address crk1POOL_ADDRESS `
  --host 0.0.0.0 `
  --port 3333 `
  --tls-cert private\pool-cert.pem `
  --tls-key private\pool-key.pem
```

The private TLS key must not be committed to Git.

## XMRig interoperability status

v0.33 implements a real `rx/0` **candidate job/submit verifier**, not a claim that stock XMRig can mine the live Crakbit scrypt chain.

The adapter deliberately uses the common RandomX job fields:

```text
job_id
blob
target
height
seed_hash
algo = rx/0
```

and places the four-byte nonce at byte offset `39`, matching the common XMRig RandomX job path.

Generate a candidate job:

```powershell
crakchain pow-xmrig-v33-job `
  --header runtime\v33\header.json `
  --job-id test-1 `
  --seed-hash <64-hex-seed> `
  --full-target <64-hex-target> `
  --output runtime\v33\xmrig-job.json
```

A captured XMRig-style submit can be recomputed against the native library:

```powershell
crakchain pow-xmrig-v33-verify-submit `
  --job runtime\v33\xmrig-job.json `
  --submit runtime\v33\xmrig-submit.json
```

**Important:** the active Crakbit chain still uses `crakpow-scrypt-v1`. An actual public XMRig pool endpoint is intentionally not advertised until the RandomX consensus format, target semantics and algorithm choice are reviewed and deliberately activated.

## Still required before RandomX activation

- benchmark representative CPUs/GPUs,
- validate the native wrapper on Windows/Linux across independent machines,
- publish independent RandomX candidate vectors,
- review validation CPU/memory DoS cost,
- decide whether upstream RandomX parameters or a project-specific configuration are appropriate,
- freeze exact hashing-blob and target semantics,
- add activation/version rules so old nodes cannot silently disagree,
- run multi-node fork/reorg tests using the candidate algorithm,
- independently review consensus changes,
- only then consider stock XMRig end-to-end interoperability.

## Production boundary

v0.33 is still a development network. It does not satisfy the remaining production gates: final PoW algorithm freeze, efficient production-grade reorg/undo design, long-lived independent public testnet, node/wallet/pool reviews, high/critical remediation, final economics, mining-centralization analysis, legal/regulatory review and an explicit human launch/no-launch decision.
