# Crakbit Chain v0.12 Alpha — History Sync, Execution Boundary & Testnet Hardening

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.12 is a larger consolidation phase. It focuses on the gaps that remained after v0.11: historical block recovery for snapshot nodes, a cleaner execution boundary for future reviewed BFT integration, safer certificate rotation, authenticated operator telemetry, explicit adversarial fixtures, multi-node soak tooling and host firewall guidance.

It deliberately does **not** claim that the current Python consensus is a production BFT implementation.

## Major additions

### 1. Genesis-anchored history archives

New module: `crakbit_chain/history_archive.py`

A full-history node can export a portable JSON archive beginning at height 1. Verification replays from genesis and checks:

- chain ID and genesis fingerprint,
- contiguous heights and previous-hash links,
- expected proposer for height/round,
- proposer Ed25519 signatures,
- transaction Merkle roots,
- signed view-change certificates,
- signed prevote/precommit quorum certificates,
- transaction signatures,
- transaction nonce ordering,
- replayed balances and fees,
- every archived state root,
- archive payload SHA-256 and final tip hash.

Commands:

```bash
crakchain archive-export \
  --genesis runtime/genesis.json \
  --data runtime/node1-data \
  --output runtime/history.json

crakchain archive-verify \
  --genesis runtime/genesis.json \
  --archive runtime/history.json
```

### 2. Snapshot-node history backfill

A node bootstrapped from a quorum-certified snapshot can import verified pre-snapshot history without replaying or mutating its current account state:

```bash
crakchain archive-import \
  --genesis runtime/genesis.json \
  --data runtime/recovered-node \
  --archive runtime/history.json
```

Import is accepted only when:

- the local node has snapshot-base metadata,
- the archive fully verifies from genesis,
- the archive reaches the local snapshot height,
- the block hash at the snapshot height exactly matches the local snapshot-base hash,
- any already-present historical rows are non-conflicting.

This fills historical block/transaction bodies for explorer/audit access while leaving balances, nonces, current height and current state untouched.

Operational visibility:

```text
GET /archive/status
```

### 3. Consensus / execution separation groundwork

New module: `crakbit_chain/execution_adapter.py`

v0.12 introduces a small finalized-block execution boundary around the ledger. It is intentionally simple, but it defines the interface a future independently reviewed BFT engine can target instead of embedding consensus assumptions directly into storage/application code.

Status:

```text
GET /execution/status
```

This is groundwork only. A reviewed external BFT core is **not yet integrated**.

### 4. Dual TLS certificate pin overlap

The validator TLS pin file now accepts either one SHA-256 fingerprint or a maximum of two fingerprints per validator.

Single pin:

```json
{
  "crk1VALIDATOR": "aaaa...64hex"
}
```

Rotation overlap:

```json
{
  "crk1VALIDATOR": [
    "oldcert...64hex",
    "newcert...64hex"
  ]
}
```

This enables an operator-controlled overlap window:

1. publish old + new pins,
2. rotate the validator certificate,
3. confirm all peers observe the new certificate,
4. remove the old pin.

The implementation rejects more than two active pins per validator to keep the rotation window bounded.

### 5. Optional authenticated monitoring endpoints

Set:

```text
CRAKBIT_MONITORING_BEARER_TOKEN=<long-random-secret-at-least-24-characters>
```

When configured, sensitive operator endpoints require:

```text
Authorization: Bearer <token>
```

Protected endpoints include metrics, operations/integrity status, transport status, archive/execution status, consensus events and equivocation evidence.

This is application-level access control only. Public-testnet monitoring should still use private networking/VPN, reverse-proxy ACLs and secret management.

### 6. Explicit Byzantine rejection fixtures

v0.12 adds automated adversarial tests for:

- duplicate validator votes,
- votes for conflicting block hashes,
- votes from unknown/forged validator identities.

These fixtures verify rejection behavior in the current research engine. They do not constitute a formal Byzantine-safety proof.

### 7. Multi-node soak monitor

New script:

```bash
python scripts/soak_test.py \
  --node https://validator1.example \
  --node https://validator2.example \
  --node https://validator3.example \
  --node https://validator4.example \
  --duration-seconds 86400 \
  --interval-seconds 5 \
  --output runtime/soak-results.jsonl \
  --fail-on-divergence
```

It records:

- node reachability,
- response latency,
- height and consensus round,
- height spread,
- same-height hash divergence,
- health observations over time.

The output is append-only JSONL so long-running public-testnet experiments can retain evidence for later analysis.

### 8. Host firewall example

`deploy/testnet/nftables.example.conf` provides a deny-by-default example that exposes only SSH from an operator allow-list and the public reverse-proxy ports by default. Validator-internal ports remain closed unless an operator explicitly restricts them to validator source addresses.

It is an example, not a drop-in production firewall policy.

## Automated tests

v0.12 adds coverage for:

- full history export and replay verification,
- archive tamper rejection,
- snapshot-node history backfill without state mutation,
- dual-certificate-pin overlap parsing,
- monitoring bearer-token checks,
- duplicate/conflicting/forged consensus vote rejection.

All earlier consensus, transport, recovery, integrity and RPC-hardening tests remain in the GitHub Actions suite.

## Remaining release blockers

v0.12 is materially more testable and recoverable, but it is still not a mainnet candidate. Remaining blockers include:

1. actual integration with an established independently reviewed BFT core,
2. explicit consensus/execution protocol versioning for that external core,
3. broad multi-process Byzantine/fork/reordering test campaigns,
4. sustained multi-host partition/load/soak results across independent hosts,
5. production secret storage/HSM or equivalent validator-key strategy,
6. hardened authenticated monitoring and alert delivery over private operator networks,
7. production reverse-proxy/firewall/DDoS architecture review,
8. independent consensus, transport and security review,
9. public testnet operation for a meaningful period before any mainnet planning.

## Suggested next phase — v0.13

The next phase should stop adding major features to the bespoke research consensus and focus on **reviewed BFT integration proof-of-concept + public-testnet automation**:

- implement a consensus adapter/process boundary,
- evaluate CometBFT-style external consensus against the current execution adapter,
- define deterministic application-hash/state transition contracts,
- add validator/node provisioning automation,
- add signed release/genesis artifact generation,
- add public faucet + read-only explorer improvements,
- run multi-host soak/partition campaigns,
- publish reproducible test results,
- prepare an external-review package.
