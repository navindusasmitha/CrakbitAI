# Crakbit Chain v0.30 Alpha — Continuous Operations / Evidence Publication

**Package:** `0.30.0a1`  
**Consensus candidate:** CometBFT `v0.40.0`  
**Governed execution:** `crakbit-execution/3`  
**Status:** continuous-operations and evidence-publication tooling — **not production mainnet**.

Production CRKBIT has **not launched**. There is no official CRKBIT presale or production token contract. v0.30 adds read-only monitoring, resumable evidence collection and publication controls; it does not automatically start a production network, change DNS, move funds or authorize custody of real value.

## Purpose

v0.29 added live validator observation, multi-operator genesis evidence, seven-day soak semantics and real fault-campaign gates. v0.30 adds the operational layer needed to keep collecting and publishing those facts over time without storing provider secrets or pretending a monitoring key is an independent validator/operator key.

## What v0.30 adds

- package/CLI `0.30.0a1`,
- signed non-secret monitor inventory for 4+ validator RPC endpoints,
- hard rejection of secret-bearing inventory fields,
- read-only live CometBFT cluster monitoring,
- signed monitoring samples with height-spread and same-height app-hash divergence checks,
- resumable hash-chained monitoring checkpoints,
- default seven-day (`604800s`) target with success ratio >= `0.99`,
- continuous collector script with checkpoint/resume behavior,
- raw evidence archive manifests with file size/SHA-256 and retention policy,
- active RPC/explorer/gateway health probes,
- redundant public-edge gate requiring at least two healthy endpoints per role by default,
- remote-signer/HSM-equivalent TCP connectivity monitoring without reading private keys,
- exact binding to the v0.29 real-evidence freeze,
- signed public release-candidate evidence bundle,
- signed operator checklist with explicit manual DNS/treasury/launch controls,
- v0.30 regression tests.

## Monitoring inventory boundary

The v0.30 monitoring inventory is intentionally non-secret. It may contain only public/operator metadata needed to read validator RPC state. Fields such as private keys, seed phrases, passwords, bearer tokens, API keys or provider credentials are rejected.

The inventory records:

```text
central_monitoring_only=true
does_not_replace_operator_attestations=true
contains_private_keys=false
contains_provider_secrets=false
production_mainnet_ready=false
```

A central monitor is useful operational evidence but does not replace independent v0.29 operator signatures or independent review.

## Resumable seven-day collection

`scripts/run_v30_monitor.py` performs read-only CometBFT probes and writes:

- one signed monitoring sample per collection interval,
- a signed checkpoint after every successful sample,
- a hash chain across sample-manifest hashes,
- sample count, success count and success ratio,
- first/last observed timestamps,
- total observed duration,
- checkpoint-complete state.

A checkpoint may be resumed after process restart. Target duration and minimum success ratio cannot silently change during the same session.

Example:

```bash
python scripts/run_v30_monitor.py \
  --inventory private/monitor-inventory-v30.json \
  --key private/monitor-evidence-key.json \
  --session-id public-testnet-7d-01 \
  --output-dir runtime/evidence/monitor-7d \
  --interval-seconds 30 \
  --target-duration-seconds 604800 \
  --minimum-success-ratio 0.99
```

The monitoring key should be a dedicated evidence-signing key, not a validator consensus key.

## Evidence archive

`archive-v30-build` hashes raw monitor logs, fault logs, state-sync records, edge measurements and other release evidence. The signed manifest records file names, roles, sizes and SHA-256 digests plus a retention period. It never embeds file contents or private keys.

The default retention recommendation is 90 days; the tool refuses a retention period below 30 days.

## Redundant public edges

`edge-v30-probe` performs a read-only HTTP health probe. The aggregate edge gate supports these roles:

- `rpc`
- `explorer`
- `gateway`

By default, at least two unique passing endpoints are required for every role. This is a redundancy/evidence gate, not a DDoS guarantee or substitute for independent capacity review.

## Protected signer monitoring

`signer-v30-probe` tests TCP connectivity to an operator-specified protected signer/HSM-equivalent endpoint and binds that observation to a prior signer-rotation drill manifest hash. The probe does not request, read or export the validator private key.

Connectivity alone does not prove secure HSM configuration. Real custody architecture still needs independent inspection and recovery testing.

## Public evidence bundle

`public-evidence-v30-build` binds:

- the exact v0.29 real-evidence freeze,
- a completed seven-day monitor checkpoint,
- success ratio >= 0.99,
- archive/retention manifest,
- redundant edge gate,
- one or more passing protected-signer monitor records,
- optional public evidence artifacts by SHA-256.

Even when the bundle gate passes it records:

```text
manual_launch_decision_required=true
automatic_launch=false
production_mainnet_ready=false
production_mainnet_launched=false
production_crkbit_launched=false
```

## Operator checklist

The signed final operator checklist requires explicit confirmation of:

- validator services,
- backups,
- alerts,
- rollback path,
- incident contacts,
- manual DNS control,
- manual treasury movement,
- manual launch approval.

A complete checklist is an operations record only. It does not launch the network.

## Real work still required

v0.30 tooling does not prove that independent hosts, providers, HSMs, public edges, reviewers or seven-day runs actually existed. Real evidence must still come from infrastructure the operators control or are authorized to test, and production consideration still requires independent security/economic/legal review plus an explicit human launch/no-launch decision.

## Security notes

- Never commit validator/private wallet keys, evidence-signing private keys, provider credentials or API tokens.
- Keep validator keys, monitoring keys, release keys and reviewer keys separate.
- Keep execution, ABCI and protected-signer surfaces private or explicitly authorized.
- Use fault/load testing only on infrastructure you own/administer or have permission to test.
- Monitoring/publication tooling must not be treated as proof of production safety by itself.
