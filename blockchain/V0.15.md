# Crakbit Chain v0.15 Alpha — Wallet UI, Public Gateway, Persistent Faucet & Mining Lab

**Status:** public-testnet / mainnet-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.15 is a large user-facing phase. It keeps the v0.14 CometBFT integration path and adds the pieces needed for people to interact with a future public testnet through a browser: a client-side wallet, a unified public gateway, read-only explorer APIs, persistent faucet limits and an opt-in proof-of-work reward lab.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Browser wallet and Web UI

The package now includes a responsive Web UI under `crakbit_chain/webui/`.

It provides:

- network overview and consensus mode,
- recent blocks / external commits,
- locally generated Ed25519 wallets,
- `crk1...` address derivation compatible with the Python wallet implementation,
- encrypted browser vault using PBKDF2-SHA256 + AES-GCM,
- wallet lock/unlock,
- import of Crakbit raw key JSON or encrypted browser vaults,
- encrypted backup export,
- client-side transaction signing,
- balance, nonce and transaction activity,
- transaction/address explorer queries,
- validator display,
- test-faucet request action,
- visible opt-in browser work-reward mining lab.

The private wallet key is not sent to the public gateway. The browser constructs and signs the canonical transaction locally and only sends the signed transaction object for broadcast.

The browser vault is a convenience feature, **not an audited hardware-wallet replacement**. Users must keep their own encrypted backup and should not use this alpha wallet for real value.

## 2. Public wallet / explorer gateway

New module:

```text
crakbit_chain/public_gateway.py
scripts/run_public_gateway.py
```

The gateway exposes one stable browser-facing API while supporting two backends:

```text
research mode
  Web UI → public gateway → research node RPC

cometbft mode
  Web UI → public gateway → CometBFT JSON-RPC
                         └→ authenticated execution-service read API
```

Public gateway endpoints include:

```text
GET  /api/health
GET  /api/network
GET  /api/services
GET  /api/account/{address}
GET  /api/transactions/{txid}
POST /api/transactions
GET  /api/blocks
GET  /api/validators
POST /api/faucet/request
GET  /api/mining/challenge
POST /api/mining/submit
```

In CometBFT mode, signed Crakbit transaction JSON is canonicalized, checked locally by the gateway and broadcast through CometBFT `broadcast_tx_sync`. The execution-service bearer token remains server-side and is never exposed to the browser.

## 3. Embedded research-node UI

The normal v0.15 research `crakchain node` now serves a compatible same-origin API and Web UI directly:

```text
http://127.0.0.1:9101/ui/
http://127.0.0.1:9101/web
```

This makes local testing simple without a separate public-gateway process. For CometBFT mode, faucet/mining proxying or public deployment, use the standalone gateway.

## 4. External execution read APIs

The authenticated v0.14/v0.15 execution service now also exposes bounded read APIs needed by the public gateway:

```text
GET /v2/info
GET /v2/account/{address}
GET /v2/transaction/{txid}
GET /v2/commits
```

The existing crash-safe `FinalizeBlock → Commit` application protocol is preserved. The gateway does not receive the private execution-service token in browser code.

## 5. Persistent testnet faucet

The test faucet now stores successful distributions in SQLite rather than process memory alone. Address cooldown therefore survives faucet restart.

It can broadcast through either:

- the original research node RPC, or
- the new public gateway, which means the same faucet service can be used with the research path or the CometBFT integration path.

The faucet remains test-only, rate bounded and capped at 100 test CRKBIT per configured request. A validator consensus key is explicitly rejected as a faucet key.

## 6. Mining Lab — proof-of-work reward, not consensus mining

New module:

```text
crakbit_chain/pow_mining.py
scripts/run_pow_mining.py
```

The Mining Lab is a **Hashcash-style testnet work-reward service**. It does not replace CometBFT and does not decide blocks.

Flow:

```text
browser requests challenge
        ↓
visible opt-in SHA-256 hashing
        ↓
server verifies nonce against target
        ↓
dedicated reward wallet signs ordinary CRKBIT transaction
        ↓
public gateway broadcasts transaction
```

The mining state database persists:

- challenge IDs and random seeds,
- difficulty and reward,
- expiry,
- solution nonce/digest,
- submission state,
- reward transaction ID,
- per-address successful-claim history.

Address cooldown and daily reward caps survive restart. The reward key must be a dedicated, funded, non-validator wallet.

**Why this is not block mining:** v0.14+ is evaluating an external BFT consensus path using CometBFT. Turning Crakbit itself into proof-of-work consensus would be a separate protocol redesign, not a Web UI feature.

## 7. Key separation

Keep all of these as separate key roles:

```text
CometBFT consensus/node keys
Crakbit research-validator keys
wallet/user keys
TLS keys
release-signing key
faucet key
mining-reward key
```

Never place validator, release or reward private keys in browser JavaScript or a public repository.

## 9. Full local public-UX stack

Generate **dedicated** faucet and mining-reward wallets:

```bash
crakchain keygen --output runtime/faucet.json
crakchain keygen --output runtime/mining-reward.json
```

Fund them only with test CRKBIT before starting reward services.

Start the gateway:

```bash
python scripts/run_public_gateway.py \
  --genesis runtime/genesis.json \
  --mode research \
  --research-rpc http://127.0.0.1:9101 \
  --faucet-url http://127.0.0.1:9400 \
  --mining-url http://127.0.0.1:9500 \
  --host 127.0.0.1 \
  --port 9600
```

Start the faucet:

```bash
python scripts/run_faucet.py \
  --genesis runtime/genesis.json \
  --key runtime/faucet.json \
  --gateway http://127.0.0.1:9600 \
  --state runtime/faucet-state.sqlite3 \
  --amount 10
```

Start the mining reward service:

```bash
python scripts/run_pow_mining.py \
  --genesis runtime/genesis.json \
  --key runtime/mining-reward.json \
  --gateway http://127.0.0.1:9600 \
  --state runtime/mining-state.sqlite3 \
  --reward 1 \
  --difficulty-bits 18
```

Then open:

```text
http://127.0.0.1:9600/ui/
```

## 10. CometBFT gateway mode

After the v0.14 execution service, ABCI bridge and CometBFT node are running, start the public gateway with:

```bash
python scripts/run_public_gateway.py \
  --genesis runtime/genesis.json \
  --mode cometbft \
  --comet-rpc http://127.0.0.1:26657 \
  --execution-url http://127.0.0.1:26659 \
  --execution-token REPLACE_WITH_LOCAL_SECRET \
  --host 127.0.0.1 \
  --port 9600
```

Do not expose the execution service or its bearer token directly to browsers or the public Internet.

## 11. What v0.15 does **not** make production-ready

The following remain release gates before any real mainnet claim:

- a sustained independent-host CometBFT testnet,
- external-consensus snapshot/state-sync completion,
- validator-set lifecycle and upgrade/governance rules,
- exhaustive crash/replay/partition/latency/load campaigns,
- remote signer/HSM-grade validator-key custody,
- an independently reviewed wallet threat model and implementation,
- hardened public RPC gateway, reverse proxy, WAF/rate limiting and DDoS plan,
- production secrets management and certificate lifecycle,
- dedicated indexed explorer infrastructure,
- signed reproducible release and genesis process,
- independent consensus/application/network/wallet security review,
- incident-response and monitoring operations,
- final economic and legal/regulatory review before any production CRKBIT implementation.

See [`docs/MAINNET_GATES.md`](docs/MAINNET_GATES.md) for the explicit release checklist.
