# Crakbit Chain v0.16 Alpha — Public-Testnet Evidence, State Checkpoints & Web Hardening

**Status:** public-testnet / mainnet-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.16 moves the v0.15 wallet/gateway experience toward a repeatable external-BFT public-testnet candidate. The phase focuses on reproducible validator labs, deterministic external-application checkpoints, a dedicated explorer index, durable public-service controls, browser security headers and repeatable crash/health evidence.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Repeatable CometBFT validator lab

New components:

```text
crakbit_chain/comet_lab.py
scripts/generate_cometbft_lab.py
```

The generator can create a local multi-node CometBFT lab using an operator-supplied CometBFT binary. It:

- initializes independent validator homes,
- keeps CometBFT consensus keys separate from Crakbit application/wallet keys,
- builds one shared CometBFT consensus genesis from the generated validator public keys,
- generates persistent-peer inventories,
- assigns independent RPC/P2P/ABCI/execution-service ports,
- creates separate external application data directories,
- creates separate execution-service bearer tokens,
- writes a non-secret lab manifest and command reference.

Example:

```bash
python scripts/generate_cometbft_lab.py \
  --cometbft /path/to/cometbft \
  --chain-id crakbit-v16-local \
  --nodes 4 \
  --output runtime/cometbft-lab
```

The intended candidate version remains CometBFT `v0.40.0`. The script does not turn an arbitrary CometBFT version into an approved production dependency; operators must independently verify the binary/version they run.

Generated validator private keys and execution tokens are local secrets and must never be committed.

## 2. External application checkpoint / state-sync adapter

New modules:

```text
crakbit_chain/external_commit_v16.py
crakbit_chain/external_state_sync.py
crakbit_chain/execution_service_v16.py
```

v0.16 can export and restore a deterministic external-application state checkpoint containing:

- exact Crakbit chain ID and genesis fingerprint,
- external consensus height,
- last CometBFT block hash known to the application,
- deterministic `crakbit-execution/2` application hash,
- sorted account balances/nonces,
- account-state root,
- fixed issued-supply total,
- complete artifact SHA-256.

Verification can require an independently trusted expected consensus height and application hash before restore.

New CLI commands:

```text
crakchain external-snapshot-export
crakchain external-snapshot-verify
crakchain external-snapshot-import
crakchain external-state-status
```

Example:

```bash
crakchain external-snapshot-export \
  --genesis runtime/genesis.json \
  --data runtime/comet-app \
  --output runtime/external-checkpoint.json

crakchain external-snapshot-verify \
  --genesis runtime/genesis.json \
  --snapshot runtime/external-checkpoint.json \
  --expected-height 1200 \
  --expected-app-hash EXPECTED_COMETBFT_APP_HASH
```

Restore requires a pristine external application database and does **not** fabricate historical commit rows before the checkpoint. The v0.16 execution store tracks `snapshot_base_height` explicitly and continues committing from `height + 1`.

### Important state-sync limitation

This is an **application checkpoint adapter**, not complete native CometBFT state-sync wiring. The project still needs reviewed integration with CometBFT snapshot offer/list/load/apply lifecycle and multi-node recovery evidence before the mainnet state-sync gate can be considered complete.

## 3. Dedicated indexed explorer database

New components:

```text
crakbit_chain/explorer_index.py
crakbit_chain/explorer_index_service.py
scripts/run_explorer_indexer.py
```

The index is a separate SQLite database used for public read workloads. It incrementally copies verified external-application commit/transaction/account information into:

- commit index,
- transaction index,
- address activity index,
- current account-state index.

It verifies the source genesis fingerprint and external-execution ownership before synchronization. Public explorer reads therefore do not need to scan or mutate the consensus/application database.

CLI:

```bash
crakchain explorer-index-sync \
  --genesis runtime/genesis.json \
  --source-data runtime/comet-app \
  --index runtime/explorer-index.sqlite3

crakchain explorer-index-status \
  --genesis runtime/genesis.json \
  --index runtime/explorer-index.sqlite3
```

Service:

```bash
python scripts/run_explorer_indexer.py \
  --genesis runtime/genesis.json \
  --source-data runtime/comet-app \
  --index runtime/explorer-index.sqlite3 \
  --host 127.0.0.1 \
  --port 9700
```

A checkpoint-restored node can expose post-checkpoint history while clearly reporting that pre-checkpoint commit history was not recreated locally.

## 4. Public gateway security profile

New `public_gateway_v16.py` and `scripts/run_public_gateway_v16.py` harden the v0.15 browser gateway.

Defaults now include:

- same-origin browser access by default instead of wildcard CORS,
- explicit CORS allow-list only when configured,
- strict Content-Security-Policy,
- `X-Content-Type-Options: nosniff`,
- `Referrer-Policy: no-referrer`,
- restrictive `Permissions-Policy`,
- frame denial,
- same-origin opener/resource policy,
- durable SQLite-backed rate limits for public transaction/faucet/mining write paths,
- no implicit trust of `X-Forwarded-For` or similar client-controlled forwarding headers,
- `/api/security/status` for operator visibility.

The SQLite limiter survives process restart. It is **not** a distributed rate-limit service. A multi-instance public deployment still requires a shared upstream limiter/API gateway/load-balancer policy and trusted-proxy design.

## 5. Faucet and Mining Lab hardening

The normal launchers now route through v0.16 wrappers:

```text
faucet_service_v16.py
pow_mining_v16.py
```

Faucet distributions/cooldowns and Mining Lab challenge/reward state were already persistent in v0.15. v0.16 also moves request limiting to durable SQLite state.

The Mining Lab remains strictly separate from consensus:

```text
Browser SHA-256 work
        │
        ▼
server verifies challenge
        │
        ▼
dedicated funded reward wallet
        │
        ▼
ordinary signed CRKBIT test transaction
```

It does not mint supply, choose validators, produce CometBFT blocks or change BFT voting power.

## 6. Multi-host health inventory

New:

```text
crakbit_chain/testnet_health.py
scripts/check_testnet_health.py
```

An operator inventory can be checked for:

- CometBFT RPC reachability,
- node ID/network identity,
- latest height,
- catch-up state,
- height spread/divergence,
- optional public-gateway application height/hash.

Example inventory:

```json
{
  "name": "Crakbit public-testnet candidate",
  "validators": [
    {"name": "validator-1", "comet_rpc": "https://node1.example/rpc", "gateway": "https://wallet.example"},
    {"name": "validator-2", "comet_rpc": "https://node2.example/rpc"}
  ]
}
```

Run:

```bash
python scripts/check_testnet_health.py \
  --inventory private/testnet-inventory.json \
  --max-height-spread 2 \
  --output runtime/evidence/health.json
```

Do not publish private validator/operator endpoints merely to satisfy this check.

## 7. Crash/replay evidence matrix

New:

```text
crakbit_chain/crash_matrix.py
scripts/run_external_crash_matrix.py
```

The isolated test matrix verifies:

1. FinalizeBlock staging persists without mutating committed state,
2. pending finalize survives a process restart,
3. Commit can complete after restart,
4. committed state survives another restart,
5. identical FinalizeBlock replay is idempotent,
6. conflicting replay is rejected,
7. a deterministic checkpoint can be restored into a fresh application DB,
8. the restored application can commit the next height.

This creates repeatable local evidence for the application boundary. It is not a substitute for killing/restarting real CometBFT and execution processes under production-like storage/network conditions.

## 8. Wallet security documentation

v0.16 adds a dedicated wallet threat model and keeps the browser wallet's design boundaries explicit:

- keys are generated/sign locally,
- encrypted browser vault is PBKDF2-SHA256 + AES-GCM,
- private keys are not intentionally submitted to the gateway,
- strict production-style CSP/security headers are available through the v0.16 gateway,
- browser extensions, compromised origins and endpoint devices remain outside the web application's complete control,
- the wallet is not an audited hardware-wallet replacement.

See `docs/WALLET_THREAT_MODEL.md`.

## 9. Validator key-custody direction

`docs/VALIDATOR_REMOTE_SIGNER.md` documents the expected production separation between:

- CometBFT consensus signing keys,
- CometBFT P2P node keys,
- Crakbit application/wallet keys,
- TLS keys,
- faucet/mining keys,
- release-signing keys.

It defines remote-signer/HSM-equivalent expectations without claiming that production HSM custody is currently deployed.

## 10. Tests / CI

v0.16 adds automated tests for:

## Mainnet gates still open

v0.16 materially improves public-testnet readiness but does **not** satisfy the production-mainnet gates. Important remaining work includes:

1. native/reviewed CometBFT state-sync integration and live recovery evidence,
2. sustained multi-host validator operation on independent infrastructure,
3. automated real partition/packet-loss/latency/restart/load campaigns with published results,
4. production reverse proxy/load balancer/WAF/DDoS capacity controls,
5. true shared/horizontal abuse controls,
6. remote-signer/HSM-equivalent validator custody deployed and drilled,
7. independent browser-wallet, consensus, application, network and cryptography review,
8. reproducible signed releases and final public genesis ceremony,
9. finalized production economics/validator incentives and applicable legal review,
10. long-lived public testnet evidence before any production-value launch decision.

## Suggested next phase — v0.17

The next phase should focus less on adding UI features and more on **real operational evidence**:

- wire the external checkpoint format into reviewed CometBFT state-sync lifecycle,
- run the generated 4-validator topology continuously across independent VPS/providers,
- automate controlled network impairment and process-kill campaigns,
- reconcile/index remote validator history and checkpoint recovery,
- deploy shared upstream rate limiting and TLS termination,
- integrate a remote signer/HSM-compatible validator flow,
- produce signed release/genesis/test evidence bundles,
- prepare a frozen independent-review candidate.

Until those gates are met, use the terms **public testnet**, **research network**, or **mainnet-candidate infrastructure** — not production mainnet.
