# Crakbit Chain v0.22 Alpha — Governed Multi-Node Testnet Campaigns

**Status:** public-testnet / review-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.22 moves the project from mostly single-node deterministic-governance mechanics into repeatable **multi-node governed testnet campaign tooling**. The goal is to make validator-set changes, activation-boundary restarts, divergence detection and signed campaign evidence repeatable before any public production-value launch is considered.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 2. Governed CometBFT lab

New module:

```text
crakbit_chain/governed_lab_v22.py
```

New command:

```text
crakchain governed-lab-create
```

The v0.22 lab generator builds on the earlier CometBFT lab but fixes an important identity requirement for governance testing: **the Crakbit application genesis validator public keys are derived from the same disposable CometBFT validator identities used by the generated local consensus network.**

That makes the v0.21 governance source validator set and the local CometBFT validator identities intentionally aligned for the governed lab.

Example:

```bash
crakchain governed-lab-create \
  --cometbft /path/to/cometbft \
  --output runtime/governed-v22-lab \
  --chain-id crakbit-v22-local \
  --nodes 4
```

Generated material includes:

```text
runtime/governed-v22-lab/
├── node1/ ... node4/            # disposable CometBFT homes
├── app1/ ... app4/              # application data directories when started
├── .secrets/                    # disposable lab-only secrets
├── application-genesis.json     # application validators aligned with CometBFT lab keys
├── governed-lab-inventory.json  # public operational inventory
├── lab-manifest.json            # lower-level CometBFT lab manifest
├── commands.txt
└── README-V22.md
```

The generated treasury and converted governance-signing key views are **disposable local-lab material only**. They exist to exercise v0.21 governance with the same local validator identities as CometBFT. They must never be promoted into a public production validator-key design.

## 3. Key-security boundary

v0.21 governance approvals are authorized by the active validator identities themselves. Therefore the local governed lab needs access to the same disposable Ed25519 validator identities for governance signatures.

v0.22 does **not** claim that this is the final production key architecture.

A production candidate still needs an independently reviewed design for:

- protected remote signing / HSM-equivalent validator custody,
- governance authorization separation or an explicitly reviewed combined-key policy,
- anti-double-sign protection,
- compromise/revocation procedures,
- independent operator key ownership,
- backup/recovery drills.

The `.secrets/*DISPOSABLE*` files generated by the local lab are intentionally unsuitable for a production deployment.

## 4. Cluster convergence / divergence monitor

New module:

```text
crakbit_chain/cluster_monitor_v22.py
```

New command:

```text
crakchain cluster-v22-check
```

Example:

```bash
crakchain cluster-v22-check \
  --inventory runtime/governed-v22-lab/governed-lab-inventory.json \
  --max-height-spread 1 \
  --output runtime/evidence/cluster-check.json
```

The monitor queries each configured node's:

- v0.21 execution `/v4/info`,
- `/v4/governance/status`,
- CometBFT `/status` RPC.

It records:

- reachability,
- application heights and hashes,
- same-height application-hash conflicts,
- active validator-set hash,
- pending governance change IDs,
- same-height governance-state conflicts,
- CometBFT catching-up state,
- cluster height spread.

A successful observation is operational evidence only. It is **not a formal consensus-safety proof**.

## 6. Validator-governance campaign plan

New module:

```text
crakbit_chain/governance_campaign_v22.py
```

New command:

```text
crakchain campaign-v22-plan-build
```

A campaign plan binds one v0.21 governance request to the expected lifecycle checkpoints:

```text
H-1  pre-emission
H    FinalizeBlock emits the validator update and records pending application state
H+1  change remains pending
H+2  target application-side validator set becomes active
```

By default it also records restart checkpoints at `H`, `H+1` and `H+2`.

Example:

```bash
crakchain campaign-v22-plan-build \
  --genesis runtime/governed-v22-lab/application-genesis.json \
  --kind join \
  --emit-height 101 \
  --change-request runtime/governance/join-validator-5-signed.json \
  --output runtime/evidence/join-campaign-plan.json
```

The campaign plan is a test/review artifact. Creating it does not mean the campaign was executed.

## 7. Signed campaign evidence

New commands:

```text
crakchain campaign-v22-evidence-build
crakchain campaign-v22-evidence-verify
```

Evidence can bind:

- exact Git source commit,
- chain/genesis identity,
- governance `change_id`,
- emit/effective heights,
- campaign plan SHA-256,
- one or more cluster/soak/restart/state-sync observation artifacts,
- dedicated evidence signer.

Example:

```bash
SOURCE_COMMIT=$(git rev-parse HEAD)

crakchain campaign-v22-evidence-build \
  --genesis runtime/governed-v22-lab/application-genesis.json \
  --key private/campaign-evidence-key.json \
  --source-commit "$SOURCE_COMMIT" \
  --plan runtime/evidence/join-campaign-plan.json \
  --observation runtime/evidence/cluster-before.json \
  --observation runtime/evidence/cluster-after.json \
  --executed \
  --output runtime/evidence/join-campaign-evidence.json
```

`--executed` is an operator assertion. A valid evidence signature authenticates that assertion and the artifact hashes; it does not create independent verification.

## 8. Recommended v0.22 campaign sequence

For a local four-node lab:

1. generate the governed lab,
2. start all four execution services, ABCI bridges and CometBFT nodes,
3. confirm cluster convergence,
4. build a validator-change request using v0.21 tooling,
5. have >2/3 current voting power approve the same request,
6. broadcast/include the governance transaction through the normal CometBFT transaction path,
7. record cluster state around `H`, `H+1`, `H+2`,
8. restart nodes at selected activation boundaries,
9. state-sync a clean node while governance state is active/pending,
10. export governance history and build signed campaign evidence.

The repository provides the deterministic state machine and evidence tooling. It does **not** claim those real runtime campaigns have been executed merely because the code exists.

## 9. Tests

v0.22 adds regression coverage for:

- generating an application genesis whose four validator public keys match four disposable CometBFT validator identities,
- exporting disposable lab-only governance signing views from local CometBFT keys,
- detecting same-height application-hash divergence,
- allowing a bounded one-height observation spread without treating different-height hashes as a conflict,
- validator campaign checkpoint semantics,
- signed campaign evidence and artifact verification,
- tamper rejection.

The existing CI continues to run the full Python suite, Go bridge tests, reproducible Python/Go build checks and direct-dependency SBOM generation.

## External gates still open

v0.22 is still **not production mainnet**. Major work that must be performed rather than merely implemented includes:

1. actually run join/remove/replace campaigns on a live four-node governed CometBFT network,
2. run activation-boundary restarts at `H`, `H+1`, and `H+2`,
3. state-sync clean hosts while a governance change is pending and after activation,
4. repeat the campaigns across independently managed VPS/providers,
5. run sustained partition, packet-loss, latency, process-kill, storage-fault and load tests,
6. deploy protected remote-signer/HSM-equivalent validator custody,
7. independently review the validator-governance and CometBFT activation semantics,
8. independently review application execution, networking/RPC, cryptography/key management and browser wallet,
9. productionize public RPC/WAF/DDoS/TLS/secret-management/monitoring,
10. finalize validator economics, CRKBIT production economics and applicable legal/regulatory review.

## Suggested next phase — v0.23

v0.23 should be an **actual public-testnet deployment / operations phase**, not just another local feature phase:

- provision four or more independently managed VPS validators,
- deploy the governed v0.22/v0.21 execution path,
- use protected operator access and private execution/ABCI surfaces,
- deploy public RPC/gateway/explorer/faucet separately,
- add TLS, DNS, monitoring and alerting,
- run 24h → 72h → 7-day soak windows,
- execute validator governance and state-sync campaigns,
- publish signed evidence and incident notes,
- keep CRKBIT test-only until production gates and independent review are satisfied.

Until the external release gates are actually satisfied, describe Crakbit Chain as **public testnet**, **review candidate**, or **mainnet-candidate infrastructure** — not production mainnet.
