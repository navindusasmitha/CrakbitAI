# Crakbit Chain v0.29 Alpha — Real Independent-Host Execution Evidence

**Package:** `0.29.0a1`  
**Consensus candidate:** CometBFT `v0.40.0`  
**Governed execution:** `crakbit-execution/3`  
**Status:** real independent-host execution/evidence tooling — **not production mainnet**.

Production CRKBIT has **not launched**. There is no official CRKBIT presale or production token contract. v0.29 does not contain an automatic production-launch command.

## Purpose

v0.28 created launch-rehearsal and independent-review evidence formats. v0.29 moves the implementation toward evidence generated from **running independent hosts** instead of adding another self-attestation-only layer.

The new live-host command actively queries CometBFT `/status` and `/abci_info`, records the observed chain/node/height/application-hash state and signs the result. Cluster, genesis, soak and fault gates then consume those signed records.

The repository still cannot prove that a host is truly independent, that a provider label is truthful or that an operator performed a real-world procedure correctly without external corroboration. Signatures provide attribution and tamper evidence, not automatic trust.

## What v0.29 adds

- package/CLI `0.29.0a1`,
- live CometBFT RPC host probing,
- signed per-validator live host observations,
- exact source/candidate/application-genesis/consensus-genesis binding,
- explicit checks that execution/ABCI surfaces are private and the validator signer is protected,
- rejection of RPC URLs containing embedded credentials,
- signed 4+ validator cluster observations,
- 4+ unique validator/operator/evidence-signer checks,
- provider and region diversity checks,
- bounded observation window and block-height spread,
- same-height application-hash divergence detection,
- signed per-operator genesis ceremony attestations,
- 4+ operator/signature genesis ceremony gate,
- signed soak evidence built from signed cluster observations,
- a hard minimum of 24h for the generic soak tool and a default mainnet-candidate target of 7 days,
- minimum soak success ratio of `0.99`,
- signed fault/recovery results bound to raw evidence-file SHA-256,
- required campaign types: restart, process-kill, partition, latency, packet-loss, load, storage, state-sync, governance and upgrade,
- v0.29 real-execution gate bound to the exact v0.28 release freeze + rehearsal gate,
- signed real-evidence freeze after the real-execution gate passes,
- explicit `production_mainnet_ready=false`, `production_mainnet_launched=false` and `production_crkbit_launched=false` throughout.

## Live validator observation

Run this from an authorized operations host against a validator RPC endpoint that is intentionally reachable from that host:

```bash
crakchain live-host-v29-probe \
  --key private/operator-evidence-key.json \
  --source-commit EXACT_CANDIDATE_COMMIT \
  --candidate-identity-sha256 CANDIDATE_IDENTITY_SHA256 \
  --application-genesis-sha256 APP_GENESIS_SHA256 \
  --consensus-genesis-sha256 CONSENSUS_GENESIS_SHA256 \
  --validator-id validator-1 \
  --operator-id operator-1 \
  --provider provider-a \
  --region region-a \
  --rpc-endpoint https://validator-1-rpc.example.net \
  --expected-chain-id crakbit-testnet \
  --execution-private-asserted \
  --abci-private-asserted \
  --signer-protected-asserted \
  --output runtime/evidence/validator-1-live.json
```

The command performs HTTP reads only. It does not submit transactions, change validator state or modify DNS. RPC URLs containing embedded credentials are rejected so secrets are not accidentally stored in evidence.

## Cluster observation

Collect one signed host observation from each independent operator within a short coordinated window, then build a cluster record:

```bash
crakchain cluster-v29-build \
  --key private/cluster-evidence-key.json \
  --host runtime/evidence/validator-1-live.json \
  --host runtime/evidence/validator-2-live.json \
  --host runtime/evidence/validator-3-live.json \
  --host runtime/evidence/validator-4-live.json \
  --output runtime/evidence/cluster-live.json
```

The default gate requires:

- at least four unique validators,
- at least four unique operators,
- at least four unique host-evidence signers,
- at least two providers,
- at least two regions,
- matching source/candidate/genesis/chain identity,
- maximum block-height spread of 2,
- observations within 5 minutes,
- no different application hashes for the same ABCI height.

## Multi-operator genesis ceremony

Each operator signs the exact application genesis, consensus genesis, chain ID and its own validator/node public identity. The aggregate ceremony gate requires at least four unique validators, operators and evidence-signing identities and requires every operator to approve the exact same genesis artifacts.

Private validator keys are never embedded in ceremony evidence.

## Seven-day soak

Repeated signed cluster observations can be aggregated:

```bash
crakchain soak-v29-build \
  --key private/soak-evidence-key.json \
  --sample runtime/soak/sample-0001.json \
  --sample runtime/soak/sample-0002.json \
  --sample runtime/soak/sample-N.json \
  --minimum-duration-seconds 604800 \
  --minimum-success-ratio 0.99 \
  --output runtime/evidence/soak-v29.json
```

The soak gate rejects a configured success target below 0.99 and rejects configured durations below 24 hours. For the intended v0.29 real-evidence campaign, use 604800 seconds (7 days) or longer.

A passing soak record requires no same-height application-hash divergence.

## Fault/recovery campaigns

Fault evidence must come from infrastructure owned/administered by the operator or explicitly authorized for testing. Each result binds a raw evidence file by SHA-256 and records authorization, recovery, application-hash reconvergence and no-data-loss assertions.

The aggregate real-execution gate requires a passing result for every required campaign type:

```text
restart
process-kill
partition
latency
packet-loss
load
storage
state-sync
governance
upgrade
```

Do not run destructive fault commands against systems you do not own or administer.

## Real execution gate

`real-gate-v29-build` verifies that:

- the supplied v0.28 release freeze is valid,
- the release freeze cryptographically binds the supplied v0.28 rehearsal gate,
- the v0.28 rehearsal gate passed,
- the live v0.29 cluster observation passed,
- the multi-operator genesis ceremony passed,
- the long-lived soak passed,
- all v0.29 evidence belongs to the exact same source/candidate,
- all ten required fault/recovery campaign types passed.

Even when every check passes, the result is only:

```text
real_execution_gate_satisfied=true
manual_launch_decision_required=true
automatic_launch=false
production_mainnet_ready=false
production_mainnet_launched=false
production_crakbit_launched=false
```

## Real evidence freeze

`real-freeze-v29-build` signs the exact v0.29 real-execution gate and optional raw evidence artifacts. It is a final evidence freeze for human/independent review; it still does not launch the chain.

## Remaining external work

The following cannot be completed by repository code alone:

- provision and operate the real independent VPS/physical validator hosts,
- independently verify operator/provider/region independence,
- run the full seven-day or longer campaign,
- execute authorized real network/storage/failure campaigns,
- deploy real HSM/remote-signer custody and independently inspect it,
- operate redundant production-style RPC/explorer/gateway edges,
- commission independent consensus/application/network/cryptography/browser-wallet review,
- complete economic-security and legal/regulatory review on the final production proposal,
- make a deliberate human launch/no-launch decision.

Until those tasks are genuinely completed and reviewed, Crakbit Chain remains public-testnet/mainnet-candidate infrastructure rather than a production mainnet.
