# Crakbit Chain v0.21 Alpha — Deterministic Validator Governance & Activation

**Status:** public-testnet / review-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.21 moves validator-set changes from operator-only rehearsal artifacts into the replicated application state machine for controlled testnet research. The application can now validate a quorum-approved validator-change transaction, commit the pending change into deterministic state, include governance state in the application hash, return the corresponding CometBFT ABCI validator update, and activate the application-side validator set at the modeled effective height.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Execution protocol v3

The governed external application uses:

```text
crakbit-execution/3
```

The execution stack remains:

```text
CometBFT v0.40.0
        │ ABCI
        ▼
Crakbit Go bridge 0.21
        │ authenticated HTTP
        ▼
/v4 execution API
        │

```

The older `/v2` execution API remains available for compatibility/research tooling, but the v0.21 bridge uses `/v4`.

## 2. Validator-governance transaction

New module:

```text
crakbit_chain/validator_governance_v21.py
```

A validator-change transaction contains a canonical request and validator approvals. Supported testnet changes are:

- `join`
- `remove`
- `replace`

The request binds:

- chain ID,
- genesis fingerprint,
- change type,
- ABCI emission height,
- modeled effective height (`emit_height + 2`),
- current validator-set hash,
- target validator-set hash,
- exact public-key/power update list.

The `change_id` is the SHA-256 hash of the canonical request. Approvals sign the canonical request/change ID and are accepted only from validators in the committed source validator set.

### Quorum rule

A governance transaction requires approval power **strictly greater than two-thirds** of the current application validator power.

For the default four-validator/equal-power lab this means 3 of 4 approvals.

Duplicate approvals, unknown validators, key/address mismatches, invalid signatures, stale source-set hashes and insufficient power are rejected.

## 3. Replicated validator-governance state

Schema version `21` adds:

```text
validator_governance_validators
validator_governance_pending
validator_governance_history
validator_governance_emissions
```

The committed application state contains:

- active validator set,
- active validator-set hash,
- at most one pending validator-set change,
- pending activation metadata.

v0.21 deliberately rejects overlapping pending validator changes. This keeps activation semantics simple enough to test and review before introducing more complex governance queues.

## 4. Governance-aware application hash

The v0.21 application hash commits to both account state and validator governance state:

```text
SHA256(canonical_json({
  protocol,
  chain_id,
  height,
  consensus_block_hash,
  accounts,
  validator_governance: {
    active_validators,
    pending
  }
}))
```

This prevents nodes from returning the same application hash while disagreeing about the pending/active validator set.

## 5. ABCI validator updates

The Go bridge now consumes `validator_updates` returned by `/v4/finalize` and converts them to CometBFT Ed25519 `ValidatorUpdate` values.

A governance request emitted at FinalizeBlock height `H` models its validator-set effect at `H+2`.

The application records the pending change at `H`; when the application reaches the modeled effective height, it activates the target validator set in the same atomic application commit path.

### Safety boundary

This is a **testnet research mechanism**, not a production governance system. It has not been independently reviewed and does not yet provide a production-grade governance key hierarchy, timelock/emergency process, slashing/jailing integration, or HSM-backed governance-signing policy.

## 6. Crash-safe FinalizeBlock / Commit

New module:

```text
crakbit_chain/external_commit_v21.py
```

v0.21 extends the staged FinalizeBlock → Commit model to mixed transfer/governance batches.

FinalizeBlock:

- validates the batch,
- re-validates governance quorum against committed validator state,
- simulates due validator activation,
- simulates the new pending change,
- computes account + governance application hash,
- persists the pending finalize request,
- returns deterministic ABCI validator updates.

Commit applies transfers, governance activation/pending state, transaction records and application metadata inside the same SQLite transaction.

Identical FinalizeBlock replay at an already committed height returns the previously recorded validator-update emission; conflicting replay is rejected.

## 7. v20 → v21 offline schema migration

New module:

```text
crakbit_chain/schema_migrations_v21.py
```

Commands:

```text
crakchain migration-v21-dry-run
crakchain migration-v21-copy
```

The migration remains offline-copy-first. Existing non-pristine schema-19/20 databases are not silently upgraded when the v0.21 execution service starts.

A v20 → v21 copy:

- preserves balances, nonces, transactions, external commits and pending FinalizeBlock state,
- initializes the governance active set from trusted genesis validator data,
- upgrades the application schema marker to 21,
- verifies the core application-state fingerprint,
- rehearses a disposable rollback back to schema 20.

Fresh pristine databases may initialize schema 21 directly.

## 8. Multi-operator signing CLI

New commands:

```text
crakchain validator-change-build
crakchain validator-change-sign
crakchain validator-change-verify
crakchain governance-status
```

Example request:

```bash
crakchain validator-change-build \
  --genesis runtime/genesis.json \
  --data runtime/comet-app \
  --kind join \
  --emit-height 101 \
  --new-public-key BASE64_ED25519_PUBLIC_KEY \
  --new-name validator-5 \
  --output runtime/governance/join-validator-5.json
```

Each current validator operator signs the same public request locally:

```bash
crakchain validator-change-sign \
  --genesis runtime/genesis.json \
  --data runtime/comet-app \
  --request runtime/governance/join-validator-5.json \
  --key private/my-validator-key.json \
  --output runtime/governance/join-validator-5-signed.json
```

Validator private keys should never be collected on one machine merely to reach quorum. For a real multi-operator test, each operator should verify the request against their trusted node state and sign locally.

## 9. Governance-aware ABCI state sync

New modules:

```text
crakbit_chain/external_state_sync_v21.py
crakbit_chain/comet_state_sync_v21.py
```

v0.21 state-sync snapshots now include:

- account state,
- active validator set,
- pending validator change (if any),
- governance hash,
- v0.21 application hash.

The snapshot remains bound to the CometBFT light-client-trusted application hash. Restore is restricted to pristine application state. Historical governance records are not fabricated during state-sync restore; only deterministic current governance state required for future execution is restored.

CLI helpers:

```text
crakchain snapshot-v21-export
crakchain snapshot-v21-verify
crakchain snapshot-v21-import
```

## External gates still open

v0.21 materially improves testnet validator lifecycle mechanics, but it does not complete production-mainnet requirements. Major open gates still include:

1. multi-host join/remove/replace campaigns on independently managed validators,
2. restart/partition/state-sync tests during pending validator activation,
3. independent review of validator-update height semantics and application/CometBFT convergence,
4. governance key separation and protected remote/HSM signing policy,
5. emergency recovery and compromised-validator governance procedures,
6. long-duration public-testnet operation with real fault/load evidence,
7. independent consensus/application/network/browser-wallet/security review,
8. complete transitive dependency/SBOM and independent reproducible-build evidence,
9. production DDoS/WAF/capacity engineering,
10. final validator economics/incentives and applicable legal/regulatory review.

## Suggested next phase — v0.22

v0.22 should focus on **multi-node validator-governance campaigns and coordinated upgrade activation**:

- one-command four-node governed CometBFT lab,
- broadcast helper for quorum-approved governance transactions,
- automated join/remove/replace campaigns,
- restart at `H`, `H+1`, and `H+2` activation boundaries,
- state-sync bootstrap with pending governance changes,
- coordinated schema/protocol upgrade activation across all nodes,
- explorer/index representation of governance transactions and validator history,
- signed campaign evidence and divergence detection,
- remote-signer/governance-key separation design.

Until external review and operations gates are actually satisfied, describe Crakbit Chain as **public testnet**, **review candidate**, or **mainnet-candidate infrastructure** — not production mainnet.
