# Crakbit Chain v0.32 Alpha — Native PoW P2P Networking / Fork Choice

**Package:** `0.32.0a1`  
**Consensus:** native Proof of Work  
**PoW bootstrap algorithm:** `crakpow-scrypt-v1`  
**P2P protocol:** `crakbit-p2p/1`  
**Ledger:** UTXO  
**Fork choice:** highest cumulative valid work  
**Status:** decentralized-network devnet alpha — **not production mainnet**.

Production CRKBIT has not launched. There is no official CRKBIT presale or production token contract.

## Purpose

v0.31 introduced real CPU-mined blocks, a UTXO ledger, block rewards, fees, difficulty, chainwork, a node RPC and a first-party pool. v0.32 adds the missing multi-node consensus/network layer so independent nodes can exchange blocks/transactions, retain competing branches and select a canonical branch by cumulative Proof-of-Work.

## Implemented in v0.32

- highest-cumulative-work branch selection,
- canonical-chain reorganization,
- canonical UTXO/transaction-state rebuild from a fully replayed candidate branch,
- disconnected-transaction + mempool reconciliation after reorg,
- median-time-past timestamp rule for new v0.32 branch validation,
- Bitcoin-style exponential block locator,
- header announcement/synchronization path followed by block fetch,
- signed Ed25519 node identities and signed chain/genesis-bound handshakes,
- static seed peers plus bounded peer discovery,
- block/transaction inventory gossip,
- P2P ping/pong,
- basic peer scoring,
- per-peer message-rate limits,
- message/block/inventory size limits,
- combined v1-compatible mining RPC + v2 P2P-aware RPC node,
- live peer/branch graph RPC inspection,
- multi-node regression test that synchronizes a mined block over the real TCP P2P implementation.

## Consensus boundary

v0.32 no longer assumes that every valid block extends the local tip. A valid side-chain block is stored in the block graph. If a fully replay-valid branch accumulates more work than the current canonical branch, the node atomically replaces canonical block/transaction/UTXO tables with the replayed higher-work state.

Equal-work branches do not automatically replace the current canonical tip. A later block that makes one branch strictly higher-work resolves the tie.

## Reorganization safety model

Before activation, the candidate branch is replayed from the deterministic genesis through the existing v0.31 consensus validator. This checks transaction signatures, UTXO spends, coinbase rules, reward/fee accounting, difficulty target, deterministic PoW seed, Merkle root, nonce bounds and Proof-of-Work.

v0.32 additionally requires each candidate block timestamp to exceed the median of the previous up-to-11 branch timestamps.

Only after replay succeeds is candidate canonical state copied into the live database. Transactions disconnected by the reorg are re-admitted to the mempool only when they remain valid against the new UTXO set.

## P2P protocol

Peers use `crakbit-p2p/1` over newline-delimited JSON/TCP during this alpha.

The first message is a signed handshake binding:

- protocol/version,
- chain ID,
- genesis hash,
- Ed25519 node identity,
- advertised P2P endpoint,
- best height/hash,
- cumulative chainwork,
- timestamp + nonce.

A node refuses peers on another chain/genesis, invalid signatures, excessive clock skew and self-connections.

Supported message families include:

```text
hello
ping / pong
getheaders / headers
getblock / block
inv
gettx / tx
getpeers / peers
```

Limits are intentionally conservative in this alpha: bounded peers, headers, inventories, orphan count, message size and per-second message rate.

## Example two-node devnet

Create one dedicated P2P identity per node. Do **not** reuse wallet/mining/pool keys:

```bash
crakchain pow-p2p-key-v32-new --output private/node1-p2p.json
crakchain pow-p2p-key-v32-new --output private/node2-p2p.json
```

Initialize both nodes with exactly the same chain configuration/genesis:

```bash
crakchain pow-network-v32-init --db runtime/node1/chain.sqlite3
crakchain pow-network-v32-init --db runtime/node2/chain.sqlite3
```

Run node 1:

```bash
crakchain pow-node-v32-run \
  --db runtime/node1/chain.sqlite3 \
  --network-key private/node1-p2p.json \
  --rpc-port 28443 \
  --p2p-port 28444 \
  --advertise 203.0.113.10:28444
```

Run node 2 with node 1 as a seed:

```bash
crakchain pow-node-v32-run \
  --db runtime/node2/chain.sqlite3 \
  --network-key private/node2-p2p.json \
  --rpc-port 29443 \
  --p2p-port 29444 \
  --advertise 203.0.113.11:29444 \
  --peer 203.0.113.10:28444
```

The addresses above are documentation examples. Use only hosts you own/administer or are authorized to operate.

## Mining compatibility

The v0.31 CPU miner and first-party pool remain usable because the v0.32 node keeps `/pow/v1/getblocktemplate`, `/pow/v1/submitblock` and transaction endpoints as compatibility aliases. Accepted local blocks and transactions are then announced to connected P2P peers.

The current first-party pool remains `crakbit-pool/1`, not standard Stratum/XMRig. RandomX and standard miner interoperability remain future work.

## Important remaining work

v0.32 is a substantial decentralization milestone, but it is still a devnet alpha. Before production consideration the project still needs a reviewed production PoW algorithm, stronger optimized sync, durable peer address management, DoS hardening, NAT/onion/privacy decisions, deeper reorg/fork adversarial testing, checkpoints only if justified, long-lived independent public-testnet operation, wallet/node/pool audits, final economics, mining-centralization analysis and applicable legal/regulatory review.

The current bootstrap PoW algorithm is **not frozen for production**.
