# Crakbit Chain v0.17 Alpha — Native CometBFT State Sync & Public-Testnet Operations

**Status:** public-testnet / mainnet-candidate infrastructure alpha. **Not a production mainnet and not suitable for custody of real value.**

v0.17 moves the v0.16 application-checkpoint work into the CometBFT ABCI snapshot lifecycle and adds signed evidence/operations tooling needed to run a serious public-testnet campaign without pretending that unperformed external tests or reviews are complete.

Production CRKBIT has **not** launched. There is no official CRKBIT presale or production token contract.

## 1. Native CometBFT ABCI snapshot lifecycle

New core module:

```text
crakbit_chain/comet_state_sync.py
```

The Go ABCI bridge now implements:

```text
ListSnapshots
OfferSnapshot
LoadSnapshotChunk
ApplySnapshotChunk
```

The snapshot manager builds on the v0.16 deterministic external-application checkpoint format and adds a CometBFT transport layer:

- deterministic snapshot bytes for a fixed committed application state,
- chunked transfer,
- SHA-256 for the complete transport artifact,
- SHA-256 for every individual chunk,
- explicit chain ID and genesis fingerprint,
- exact committed height,
- deterministic application hash,
- fixed-supply invariant verification,
- restore only into pristine application state,
- no fabrication of pre-checkpoint commit history.

The target application accepts a snapshot only when the application hash embedded in the offered snapshot metadata matches the application hash supplied by CometBFT in `OfferSnapshot`. The complete reconstructed snapshot is then independently re-verified against that trusted hash before state import.

This means snapshot metadata itself is not treated as a trust anchor.

### Materializing a snapshot

Snapshots are materialized explicitly after a committed height:

```bash
crakchain comet-snapshot-materialize \
  --genesis runtime/genesis.json \
  --data runtime/comet-app
```

Status:

```bash
crakchain comet-snapshot-status \
  --genesis runtime/genesis.json \
  --data runtime/comet-app
```

The current implementation does not automatically create a snapshot after every block. Operators choose snapshot cadence and retention.

## 2. v0.17 execution service

New launcher:

```text
scripts/run_execution_service_v17.py
```

It retains the authenticated `crakbit-execution/2` FinalizeBlock/Commit API and adds authenticated `/v3/state-sync/*` endpoints used by the Go bridge.

Example:

```bash
python scripts/run_execution_service_v17.py \
  --genesis runtime/genesis.json \
  --data runtime/comet-app \
  --token "$CRAKBIT_EXECUTION_TOKEN" \
  --host 127.0.0.1 \
  --port 26659
```

The execution-service token must remain server-side and must not be exposed to the browser wallet or public RPC clients.

## 3. CometBFT Go bridge v0.17

`cometbft-app/main.go` now routes the ABCI state-sync methods to the authenticated execution service.

The bridge still handles:

- `Info`,
- `CheckTx`,
- `PrepareProposal`,
- `ProcessProposal`,
- `FinalizeBlock`,
- `Commit`,
- minimal application query support,

and now additionally handles the complete ABCI snapshot lifecycle above.

The selected integration candidate remains CometBFT `v0.40.0`. Exact dependency/version review remains a release gate.

## 4. Signed public-testnet evidence bundles

New:

```text
crakbit_chain/evidence_bundle.py
```

CLI:

```text
crakchain evidence-build
crakchain evidence-verify
```

A bundle cryptographically commits to:

- exact Git source commit,
- declared CometBFT version,
- application genesis fingerprint and genesis-file SHA-256,
- optional signed release-manifest artifact,
- supplied health/fault/recovery/soak evidence files and their SHA-256 hashes,
- dedicated Ed25519 evidence signer identity.

The bundle deliberately contains the following conservative claims by default:

```text
independent_host_operation_verified = false
independent_security_review_completed = false
production_mainnet_ready = false
```

Creating a signed bundle therefore records evidence; it does not manufacture evidence that has not been produced.

Example:

```bash
crakchain evidence-build \
  --genesis runtime/genesis.json \
  --key private/evidence-signing-key.json \
  --source-commit <exact-git-commit> \
  --cometbft-version v0.40.0 \
  --evidence runtime/evidence/health.json \
  --evidence runtime/evidence/fault-campaign.json \
  --output runtime/evidence/public-testnet-evidence.json
```

Never commit the evidence-signing private key.

## 5. Controlled fault-campaign runner

New:

```text
crakbit_chain/fault_campaign.py
scripts/run_fault_campaign.py
```

The runner consumes:

- an inventory of validator RPC/gateway endpoints,
- an operator-supplied campaign JSON,
- explicit fault and recovery commands for each step.

It records validator health before, during and after each step, command return codes/output and whether the network recovered.

**The default is dry-run.** Commands execute only with `--execute`.

Each step is required to contain a recovery command. The runner attempts recovery even when the fault command itself fails.

This tooling can support controlled scenarios such as process restart, operator-provided latency/packet-loss injection or load generation, but the repository does not claim those campaigns have already been executed across independent providers.

## 6. Public-testnet edge profile

New deployment scaffold:

```text
deploy/public-testnet-edge/
```

The NGINX profile provides a single controlled testnet edge with:

- TLS 1.2/1.3 termination using operator-mounted certificates,
- HTTP-to-HTTPS redirect,
- request body/connection limits,
- separate transaction/faucet/Mining-Lab write limits,
- general API limits,
- upstream timeouts,
- controlled forwarding headers,
- basic security headers.

One NGINX edge can centralize limits for multiple gateway workers behind that host. It is **not** a globally distributed rate limiter or complete DDoS/WAF architecture. Multiple edge hosts still require a shared upstream control plane.

Execution-service, ABCI, remote-signer and validator operator interfaces must remain private/authorized surfaces.

## 7. Remote-signer configuration helper

New:

```text
scripts/configure_comet_remote_signer.py
```

The helper updates only CometBFT's `priv_validator_laddr` setting and makes a backup of `config.toml` by default.

It does **not**:

- read or copy the validator private key,
- implement an HSM,
- migrate a validator key,
- make a public signer transport safe automatically.

Loopback TCP signer endpoints are allowed by default. Non-loopback signer addresses require an explicit override and still require separately authenticated/encrypted private transport, firewalling and signer review.

See `docs/VALIDATOR_REMOTE_SIGNER.md`.

## 8. Tests and CI

v0.17 adds Python tests for:

- deterministic CometBFT snapshot materialization,
- trusted application-hash enforcement,
- snapshot chunk restore into pristine state,
- bad-chunk retry/refetch behavior,
- signed evidence bundles and tamper detection,
- fault-campaign dry-run/recovery-plan requirements.

The Go bridge tests now also exercise ListSnapshots/OfferSnapshot/LoadSnapshotChunk/ApplySnapshotChunk framing.

## What v0.17 does not prove

Implementation is not the same as operational evidence. The following remain open until they are actually performed and independently reviewable:

1. sustained 4-validator operation on independently managed hosts/providers,
2. successful end-to-end live CometBFT state-sync recovery on those hosts,
3. real partition/packet-loss/latency/process-kill/sustained-load campaigns with raw evidence,
4. tested external remote signer/HSM-equivalent deployment,
5. multi-operator genesis ceremony with independently held keys,
6. independently reviewed consensus/application/network/wallet security,
7. production DDoS/WAF/capacity engineering,
8. production validator economics and applicable legal/regulatory review.

## Suggested next phase — v0.18

v0.18 should be an **evidence-and-review freeze** rather than another large feature expansion:

- deploy the v0.17 candidate across independent hosts,
- run a long-lived public testnet,
- execute and publish repeatable failure campaigns,
- prove clean-host state-sync/bootstrap recovery,
- reconcile explorer/index state against consensus state,
- exercise a protected remote signer,
- produce signed source/genesis/release/evidence artifacts,
- freeze a review candidate,
- commission independent consensus/application/network/wallet review,
- remediate findings before any production-mainnet decision.

Until those gates are satisfied, use **public testnet**, **research network** or **mainnet-candidate infrastructure** — not production mainnet.
