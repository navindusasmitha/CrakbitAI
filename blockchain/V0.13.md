# Crakbit Chain v0.13 Alpha — External-Consensus PoC, Signed Releases, Faucet & Testnet Automation

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.13 is a larger phase that shifts effort away from extending the bespoke Python consensus and toward the operational and protocol boundaries needed to evaluate a reviewed external BFT core. It also adds signed release/genesis tooling, independent-host provisioning scaffolds, a strictly test-only faucet, improved explorer APIs and reproducible soak evidence processing.

## Major additions

### 1. Deterministic application protocol boundary

New module: `crakbit_chain/app_protocol.py`

Protocol identifier:

```text
crakbit-execution/1
```

The adapter exposes deterministic, non-mutating operations for:

- current application state / application hash,
- signed transaction validation,
- ordered transaction-batch preview,
- transaction Merkle root calculation,
- simulated next state root,
- explicit fee-recipient and total-fee accounting.

The application hash commits to chain ID, height, finalized block hash and sorted account balance/nonce state while excluding consensus-local metadata.

v0.13 deliberately does **not** expose an external state-finalization endpoint. That remains gated on a reviewed BFT integration and a reviewed crash/replay contract.

### 2. Isolated execution-service process PoC

New module and launcher:

```text
crakbit_chain/execution_service.py
scripts/run_execution_service.py
```

It runs loopback by default and requires a bearer token for every non-health operation:

```text
GET  /health
GET  /v1/info
POST /v1/check-tx
POST /v1/preview-batch
```

Example:

```bash
python scripts/run_execution_service.py \
  --genesis runtime/genesis.json \
  --data runtime/node1-data \
  --token REPLACE_WITH_LONG_RANDOM_SECRET
```

This process boundary is intended for integration experiments with an established BFT engine without granting it an unaudited mutation path.

### 3. Signed genesis / release artifacts

New module: `crakbit_chain/release_artifacts.py`

New CLI commands:

```bash
crakchain release-build \
  --genesis runtime/genesis.json \
  --key runtime/release-signing-key.json \
  --version 0.13.0a1 \
  --artifact dist/crakbit-chain.whl \
  --output runtime/release-0.13.json

crakchain release-verify \
  --manifest runtime/release-0.13.json \
  --genesis runtime/genesis.json \
  --expected-signer crk1EXPECTED_RELEASE_SIGNER \
  --artifact-dir dist
```

The signed envelope commits to:

- release format/version,
- chain ID and network name,
- genesis fingerprint,
- exact genesis file SHA-256,
- release artifact file names, sizes and SHA-256 hashes,
- dedicated release signer identity.

A release-signing key should be separate from validator consensus keys.

### 4. Independent-host validator provisioning scaffolds

New script:

```bash
python scripts/provision_testnet.py \
  --genesis runtime/genesis.json \
  --output runtime/operator-bundles
```

It creates non-secret per-validator operator scaffolds containing:

- validator/public identity metadata,
- mTLS/pin environment templates,
- peer-pin overlap templates,
- per-host deployment checklist,
- public inventory and quorum metadata.

The generated bundles intentionally contain no validator private keys, TLS private keys or monitoring tokens.

### 5. Strictly test-only faucet service

New module and launcher:

```text
crakbit_chain/faucet_service.py
scripts/run_faucet.py
```

Example:

```bash
python scripts/run_faucet.py \
  --genesis runtime/genesis.json \
  --key runtime/faucet.json \
  --rpc http://127.0.0.1:9101 \
  --amount 10 \
  --cooldown-seconds 3600 \
  --global-rpm 10
```

The faucet:

- is disabled unless explicitly enabled by the launcher/environment,
- refuses validator consensus keys,
- caps each request at 100 test CRKBIT,
- enforces a per-address cooldown,
- applies a global per-process request limit,
- signs ordinary chain transactions and submits them through the node RPC,
- represents test units only and no production value.

Because the current devnet allows one pending transaction per sender, the faucet can temporarily return a busy/failure response until its previous transfer finalizes.

### 6. Read-only explorer API improvements

The v0.13 node adds bounded public read APIs:

```text
GET /explorer/summary
GET /explorer/blocks?limit=20
GET /explorer/address/{address}?limit=50
GET /protocol/status
```

Explorer queries are deliberately bounded. Address activity currently uses a capped historical scan and is not a substitute for a dedicated indexed explorer database.

### 7. Reproducible soak-test summaries

Existing multi-node soak JSONL output can now be summarized with:

```bash
python scripts/soak_summary.py \
  --input runtime/soak-results.jsonl \
  --output runtime/soak-summary.json
```

The summary captures:

- sample count and duration,
- same-height hash-divergence samples,
- samples with unreachable nodes,
- maximum observed height spread,
- latency observations/average/max/approximate p95,
- per-node failure counts.

This is operational evidence, not a formal consensus-safety proof.

### 8. External-review preparation

New documents:

- `docs/EXECUTION_PROTOCOL_V1.md`
- `docs/EXTERNAL_REVIEW_PACKAGE.md`

The review package defines source files, signed artifacts, soak evidence, fault evidence, recovery evidence and review questions that should accompany an independent consensus/network/security review.

## Security position

v0.13 is intentionally a transition phase. It improves deterministic application boundaries and testnet operations, but **does not integrate a reviewed BFT core yet**.

Still required before mainnet consideration:

1. integrate or migrate to an established independently reviewed BFT core,
2. define and review the authenticated mutating finalize/commit application contract,
3. test crash/replay semantics across the external-consensus boundary,
4. run sustained independent-host partition/latency/load/soak campaigns,
5. harden faucet/public RPC with upstream DDoS/reverse-proxy controls,
6. adopt production-grade validator and release-key custody/HSM-equivalent controls,
7. publish signed reproducible testnet releases and genesis artifacts,
8. commission independent consensus/network/security review,
9. operate a meaningful public testnet before any production/mainnet planning.

## Suggested next phase — v0.14

The next major phase should focus on a **real external reviewed-BFT integration test network**, not new bespoke consensus features:

- select the external BFT implementation and pin its reviewed version,
- build the authenticated finalize/commit application protocol,
- persist deterministic application hashes for external consensus,
- add crash-safe external-consensus replay/recovery tests,
- produce signed testnet release bundles and genesis ceremony tooling,
- deploy validators on multiple independent hosts,
- run automated partition/latency/load campaigns,
- publish soak/fault results,
- harden the testnet faucet/explorer and monitoring stack,
- prepare the first external review candidate.
