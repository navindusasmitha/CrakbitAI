# Crakbit Chain v0.7 Alpha — Durable Peer Replay Protection + Quorum Snapshot Recovery

**Status:** research/devnet alpha. Not production-ready and not suitable for custody of real value.

v0.7 focuses on two operational failure modes left open by v0.6: peer-authentication replay state disappearing after a validator restart, and the lack of a quorum-certified way to bootstrap state without replaying the entire historical chain.

## What v0.7 Adds

### Persistent validator request replay protection

Validator-to-validator requests are still authenticated with Ed25519 signatures over the HTTP method, path, request-body hash, validator identity, timestamp and nonce.

v0.7 persists accepted `(validator, nonce)` replay keys in a small SQLite database when `CRAKBIT_DATA_DIR` is configured. This means restarting the validator process does not immediately erase the replay cache.

The replay database defaults to:

```text
<CRAKBIT_DATA_DIR>/peer-replay.sqlite3
```

Old entries are removed after the bounded authentication window.

### Quorum-certified state snapshots

Each validator can already sign its current deterministic account-state snapshot. v0.7 can now combine individual validator snapshot signatures only when at least the configured strict `>2/3` quorum signed the **same snapshot hash**.

For the default four-validator devnet, a certified snapshot requires 3 matching validator signatures.

A certificate cannot mix signatures from different heights or different state roots because signatures are grouped and verified by the exact snapshot hash.

### Snapshot fetch

With a running validator set:

```bash
crakchain snapshot-fetch \
  --genesis runtime/genesis.json \
  --output runtime/snapshot-cert.json
```

The command queries every configured validator's `/snapshot/latest` endpoint, independently verifies each Ed25519 signature and creates the newest snapshot hash that reaches quorum.

If validators disagree and no state hash reaches quorum, snapshot creation fails instead of selecting a minority state.

### Snapshot verification

```bash
crakchain snapshot-verify \
  --snapshot runtime/snapshot-cert.json \
  --genesis runtime/genesis.json
```

Verification checks:

- certificate format,
- chain ID,
- genesis fingerprint,
- deterministic account ordering,
- account-state root,
- issued-supply conservation,
- snapshot hash,
- validator identities,
- validator public keys,
- unique signers,
- individual Ed25519 signatures,
- strict validator quorum.

### Safe snapshot import

A certified snapshot can bootstrap only a **fresh height-zero database**:

```bash
crakchain snapshot-import \
  --snapshot runtime/snapshot-cert.json \
  --genesis runtime/genesis.json \
  --data runtime/recovered-node
```

The import records:

```text
snapshot_base_height
snapshot_base_hash
snapshot_accounts_root
snapshot_certificate_hash
```

The imported node starts from the certified account state and finalized block hash. Historical blocks before the snapshot are not recreated locally.

The restriction to a fresh database is deliberate: v0.7 refuses to silently overwrite existing finalized local history.

### Bootstrap a node directly from a certificate

```bash
crakchain node \
  --genesis runtime/genesis.json \
  --key runtime/node4/validator.json \
  --data runtime/node4-recovered \
  --bootstrap-snapshot runtime/snapshot-cert.json \
  --port 9104
```

After startup, normal peer synchronization can request blocks newer than the imported snapshot height.

### Recovery status

The v0.7 node wrapper adds:

```text
GET /recovery/status
```

It reports whether the local database was snapshot-bootstrapped and whether peer replay protection is using the persistent SQLite store.

## What v0.7 Does Not Claim

v0.7 does **not** make Crakbit Chain production-ready.

Remaining major blockers include:

- the consensus lock still lacks a mature proof-based cross-round unlock rule,
- validator transport can require HTTPS but does not yet provision or rotate mTLS certificates,
- snapshot certificates authenticate state but do not reconstruct historical blocks before the snapshot,
- snapshot transfer is not chunked or bandwidth-controlled,
- the chain has not undergone formal safety/liveness review,
- long-running Byzantine/partition/load testing is still required,
- key management is still development-grade,
- no independent audit has been completed.

## Recovery Trust Model

A node importing a v0.7 snapshot trusts the configured validator set according to the same `>2/3` quorum assumption used by the development consensus. A single validator snapshot is useful for diagnostics but is not sufficient for fast-state bootstrap.

This recovery mechanism is a development milestone, not a substitute for an independently reviewed consensus and state-sync protocol.

## Next Engineering Phase — v0.8

Planned priorities:

1. Replace/review the conservative consensus lock with a mature cross-round BFT lock/unlock design or migrate to a reviewed BFT core.
2. Add mutually authenticated TLS validator transport with certificate pinning/rotation.
3. Add snapshot chunking, transfer limits and resumable state sync.
4. Add explicit snapshot/base-height awareness to block/history APIs.
5. Add crash, corruption and interrupted-import recovery tests.
6. Add long-running partition, latency, Byzantine and load test harnesses.
7. Add Grafana dashboards and alert rules around Prometheus metrics.
8. Add public-testnet deployment manifests and operator runbooks.
9. Add faucet abuse controls and improve wallet/explorer testnet UX.
10. Commission an external consensus/network review before any public-value use.
